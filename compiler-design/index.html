    Chapter 1 — Introduction to Compiling

    1.1 Compilers

    Definition. A compiler is a program that reads a program written in a source language and translates it into an equivalent program in a target language, while reporting any errors found during the translation process.

              +------------+
Source →  |  COMPILER  |  → Target program
Program   +------------+
               |
               v
          Error messages

    Compiler vs Interpreter

    AspectCompilerInterpreter
    ExecutionTranslates whole program first, then runs the target codeTranslates and executes statement-by-statement
    SpeedFaster execution after compilationSlower, translation overhead every run
    Error detectionAll errors detected before executionErrors detected only when that line is reached
    OutputProduces a separate target file (e.g. .exe)No separate target file
    ExamplesC, C++ compilersPython (classic), shell scripts

    Advantages of compilation: fast repeated execution, whole-program error checking, opportunity for optimization.
    Limitations: compilation step needed before running; harder to give instant interactive feedback.

    Basic organization: a compiler is commonly split into a front end (analysis: lexical, syntax, semantic) and a back end (synthesis: intermediate code, optimization, target code generation).

    1.2 Analysis of the Source Program

    Compilation is often viewed as analysis (breaking the source program down and understanding its meaning) followed by synthesis (constructing the target program from that understanding).

    StageReceivesProducesTypical error caught
    Lexical analysisStream of charactersStream of tokensIllegal character, malformed number
    Syntax analysisStream of tokensParse tree / syntax treeMissing semicolon, unbalanced parentheses
    Semantic analysisSyntax treeAnnotated (decorated) syntax treeType mismatch, undeclared variable

    Example. For the statement position = initial + rate * 60:

    • Lexical analysis produces tokens: id(position) = id(initial) + id(rate) * num(60)
    • Syntax analysis builds a tree reflecting that * binds tighter than +.
    • Semantic analysis checks that rate and 60 are compatible types (and may insert a conversion, e.g. inttofloat, if rate is real and 60 is an integer literal).

    Chapter 2 — Simple One-Pass Compiler

    2.1 Syntax Definition

    Grammar
    A formal description of a language's syntax, made of terminals, non-terminals, productions, and a start symbol.
    Terminals
    Basic symbols from which strings are formed (tokens).
    Non-terminals
    Syntactic variables denoting sets of strings; used to organize the grammar.
    Production
    A rule of the form A → α specifying how a non-terminal expands.
    Start symbol
    The distinguished non-terminal representing the whole language.
    Derivation
    A sequence of productions applied to derive a string from the start symbol.
    Parse tree
    Tree showing how a string is derived: root is the start symbol, leaves are terminals.
    Ambiguity
    A grammar is ambiguous if some string has more than one parse tree.

    Example grammar for simple arithmetic expressions:

    E → E + T | T
T → T * F | F
F → ( E ) | id

    Derivation of id + id * id (leftmost):

    E ⇒ E + T ⇒ T + T ⇒ F + T ⇒ id + T ⇒ id + T * F ⇒ id + F * F ⇒ id + id * F ⇒ id + id * id

    2.2 Syntax-Directed Translation

    Syntax-directed translation (SDT) attaches a semantic action (a rule/fragment of code) to each grammar production; as the parser recognizes a production, it executes the associated action, producing a translation.

    Worked example. Grammar with translation rules for converting an expression to postfix:

    ProductionSemantic rule
    E → E1 + TE.t = E1.t || T.t || '+'
    E → TE.t = T.t
    T → idT.t = id.lexeme

    Grammar → parse structure → semantic action → translation for a + b:

    Parse: E(E(T(id:a)) + T(id:b))
Actions applied bottom-up: T.t="a"; T.t="b"; E.t = "a" || "b" || "+" = "ab+"
Result: postfix "ab+"

    2.3 Parsing

    A parser takes the token stream from the lexical analyzer and determines whether it can be generated by the grammar of the source language, producing a parse tree (explicit or implicit) and reporting syntax errors (e.g. missing operator, unmatched parenthesis) with diagnostics. Parsing is discussed conceptually here; the algorithms (recursive descent, predictive, shift-reduce, LR) are covered in Chapter 4.

    2.4 Translation of Simple Expressions

    Consider expressions built from identifiers, constants, + - * /, and parentheses, with the usual precedence (*,/ bind tighter than +,-) and left associativity.

    Example 1 — 9 - 5 + 2
    1. Original expression: 9 - 5 + 2
    2. Structure (left-associative, same precedence): ((9 - 5) + 2)
    3. Translation steps to postfix: push 9, push 5, apply - → "9 5 -", push 2, apply + → "9 5 - 2 +"
    4. Final translated form: 9 5 - 2 +
    5. Verification: evaluating postfix — (9-5)=4, (4+2)=6; evaluating infix — (9-5)+2 = 6. ✔ Match.
    Example 2 — a + b * c
    1. Original: a + b * c
    2. Structure: a + (b * c) (precedence)
    3. Postfix construction: a, b, c, apply * → "a b c *", apply + → "a b c * +"
    4. Final form: a b c * +
    5. Verification: with a=2,b=3,c=4: postfix gives 3*4=12, 2+12=14; infix gives 2+(3*4)=14. ✔
    Example 3 — stack-machine instructions for (a + b) * c 
    push a
push b
add
push c
mul
    Stack states: [a] → [a,b] → [a+b] → [a+b, c] → [(a+b)*c]. Final top-of-stack holds the result. ✔ matches expected value.

    2.5 Symbol Table

    Purpose: stores information about each identifier — name, type, scope, and (later) memory location — so that later phases (semantic analysis, code generation) can retrieve it.

    NameTypeScopeOffset
    aintglobal0
    bfloatglobal4

    Entries are created when a declaration is processed (lexical analyzer or a declaration-handling routine inserts the name; semantic analysis fills in type/scope). Entries are looked up whenever the identifier is used, e.g. during type checking or address computation.

    2.6 Abstract Stack Machines

    An abstract stack machine evaluates expressions using a stack; typical instructions: push (load a value/variable onto the stack), pop/store (remove top and store into a variable), and arithmetic ops (add, sub, mul, div) that pop two operands and push the result.

    Worked example — x = a + b * c

    #InstructionStack after execution
    1push b[b]
    2push c[b, c]
    3mul[b*c]
    4push a[b*c, a]
    5add[a + b*c]
    6store x[] (x := a+b*c)
    Verification: with a=2,b=3,c=4 → b*c=12, a+12=14, so x=14; direct evaluation of a+b*c = 2+12=14. ✔

    Chapter 3 — Lexical Analysis

    3.1 Role of the Lexical Analyzer

    Reads the source character stream and groups characters into lexemes, classifying each lexeme into a token according to a pattern, discarding whitespace/comments, and reporting lexical errors (e.g. illegal character). It hands tokens to the parser (often on demand, one at a time).

    TermMeaningExample
    TokenA category/abstract symbol representing a kind of lexical unitid, num, relop
    LexemeThe actual sequence of characters matchedcount, 123, <=
    PatternThe rule (often a regular expression) describing the set of lexemes for a tokenletter(letter|digit)* for id
    For total = total + rate * 5; the lexemes/tokens are: total→id, =→assign, total→id, +→plus, rate→id, *→mult, 5→num, ;→semicolon.

    3.2 Input Buffering

    Scanning character-by-character with a system call per character is slow, so a lexer reads input into a buffer in large blocks.

    Double buffering scheme: two buffers of size N are used; a pointer lexemeBegin marks the start of the current lexeme and a pointer forward scans ahead. When forward reaches the end of one buffer, the other buffer is refilled; a sentinel (eof marker) is placed at the end of each buffer so a single test (forward pointer hit sentinel?) handles both "end of buffer, reload" and "end of input" cases, avoiding a separate bounds check on every character.

    Buffer 1:  E  =  M  *  C  * *  2  eof
Buffer 2:  ...next block...       eof
           ^lexemeBegin      ^forward

    Lookahead/retraction: the lexer may need to look one or more characters beyond the current lexeme to decide the pattern (e.g. distinguishing < from <=); if the extra character does not belong, forward is retracted by one.

    This scheme improves efficiency because most character tests reduce to a single sentinel check instead of two comparisons (buffer bound and character value).

    3.5 Regular Expression → NFA — Thompson's Construction

    Construction rules (each fragment has exactly one start state and one accepting state):
    • Symbol a: start --a--> accept (single transition on a).
    • Concatenation r·s: accept state of r's fragment is connected by an ε-transition to the start state of s's fragment; r's start becomes the overall start, s's accept becomes the overall accept.
    • Union r|s: new start state has ε-transitions to both r's start and s's start; both r's accept and s's accept have ε-transitions to a new common accept state.
    • Kleene star r*: new start and new accept states are added; new start has ε-transitions to r's start and directly to new accept (zero occurrences); r's accept has ε-transitions back to r's start (repeat) and to new accept (stop).

    Worked example — building the NFA for (a|b)*abb step by step.

    Step 1 — Parse into subexpressions: (a|b), then *, then concatenated with a, b, b.

    Step 2 — Fragment for a: N1: state 0 --a--> state 1.

    Step 3 — Fragment for b: N2: state 2 --b--> state 3.

    Step 4 — Union a|b: new start 4, new accept 5.
    4 --ε--> 0, 4 --ε--> 2, 1 --ε--> 5, 3 --ε--> 5.
    Fragment N3 = start 4, accept 5.

    Step 5 — Star (a|b)*: new start 6, new accept 7.
    6 --ε--> 4 (enter loop body), 6 --ε--> 7 (skip body),
    5 --ε--> 4 (repeat), 5 --ε--> 7 (exit).
    Fragment N4 = start 6, accept 7.

    Step 6 — Concatenate with literal a, b, b: Build a --a→ 9 (fragment N5: 8 to 9), 10 --b--> 11 (N6), 12 --b--> 13 (N7).
    Connect: 7 --ε--> 8, 9 --ε--> 10, 11 --ε--> 12.

    Final NFA: overall start = 6, overall accept = 13, with the ε-transitions listed above connecting every fragment (13 states total, numbered 0–13).

    Verification:
    • abb: 6→ε→6/4→ε→0 →a→1→ε→5→ε→7→ε→8→a? — take the path 6-ε-4-ε-0-a-1-ε-5-ε-7-ε-8; but next input is "b" not "a" for the literal-a fragment, so instead take the star-exit branch immediately: 6-ε-7-ε-8 -a→ 9 -ε→10 -b→11 -ε→12 -b→13 (accept). Accepted. ✔
    • aabb: loop through the star once consuming "a" (6-ε-4-ε-0-a-1-ε-5-ε-4... one more pass is unnecessary here since after one loop we exit via 5-ε-7), then literal a,b,b consumes "abb": accepted. ✔
    • ab (too short, no trailing "abb" pattern completed cleanly with only 2 chars): rejected, since the literal tail needs 3 more symbols after zero-or-more loop consumption and only 2 symbols are available in total — no accepting path exists. ✔

    3.6 NFA → DFA — Subset Construction

    Definitions:
    • ε-closure(s): set of NFA states reachable from state s using only ε-transitions (including s itself).
    • move(T, a): set of NFA states to which there is a transition on input symbol a from some state in set T.
    Algorithm:
    1. Start state of DFA = ε-closure(start state of NFA).
    2. For each unmarked DFA state T and each input symbol a: compute U = ε-closure(move(T,a)). If U is new, add it as a DFA state.
    3. Repeat until no new states are generated.
    4. A DFA state is accepting if it contains at least one NFA accepting state.

    Worked example — subset construction on a small NFA for a(b|c)* with states: 0 --a--> 1; 1--ε-->2; 2--ε-->3 (loop entry) ; 2--ε-->5(exit,accept); 3--b-->4, 4--ε-->2 style loop; 3 in union with 3'--c-->4' also looping back to 2. To keep the table concrete we summarize the reachable NFA sets directly:

    DFA StateNFA State SetInput aInput bInput cAccepting?
    A{0}B--No
    Bε-closure(move({0},a)) = {1,2,3,3',5}-CCYes (contains 5)
    Cε-closure(move(B,b)∪move(B,c)) = {4,4',2,3,3',5}-CCYes (contains 5)

    Calculation shown explicitly: move(B,b) follows the b-transition out of state 3 to state 4; ε-closure(4) then reaches 2, 3, 3', 5 (looping back into the star body and out to accept). Since C's b/c transitions map back to the same NFA set C, no new states are produced — the subset construction terminates.

    Verification: string "abc": A→a→B→b→C→c→C, ends in accepting state C. Accepted, matching a(b|c)*. ✔ String "b" alone: A has no transition on b, so it is a lexical/automaton error path — rejected, correctly, since the language requires a leading "a". ✔

    3.7 Regular Expression → DFA

    The course approach is the two-step pipeline: RE → NFA (Thompson) → DFA (subset construction), exactly as carried out in 3.5 and 3.6 above (the NFA of §3.5 could be fed into the subset-construction algorithm of §3.6 to obtain a DFA directly).

    Additional material (not the primary syllabus method): a DFA can also be built directly from a regular expression via the "direct method" using the syntax tree of the RE and the functions nullable, firstpos, lastpos, and followpos, skipping the intermediate NFA. This is presented only as supporting/advanced knowledge; the RE→NFA→DFA pipeline is the examinable procedure emphasized here.

    Chapter 4 — Syntax Analysis

    4.1 Role of the Parser

    Takes the token stream from the lexical analyzer, verifies it conforms to the source-language grammar, builds a parse tree (explicit or implicit), reports syntax errors with recovery where possible, and passes the tree (or an equivalent structure) to semantic analysis.

    4.2 Context-Free Grammar (CFG)

    A CFG is a 4-tuple (N, T, P, S): non-terminals, terminals, productions, start symbol.

    Sentential form
    Any string derivable from the start symbol (may contain non-terminals).
    Sentence
    A sentential form containing only terminals.
    Leftmost derivation
    At each step, the leftmost non-terminal is expanded.
    Rightmost derivation
    At each step, the rightmost non-terminal is expanded.
    Grammar: S → aSb | ε. Leftmost derivation of aabb: S ⇒ aSb ⇒ aaSbb ⇒ aabb.

    4.3 Writing a Grammar

    Step-by-step example — grammar for simple arithmetic with parentheses, identifiers, numbers:

    E → E + T | E - T | T
T → T * F | T / F | F
F → ( E ) | id | num

    Precedence is encoded by layering non-terminals (E for lowest precedence +/-, T for */ , F for atoms); associativity (left) is encoded by left recursion (E → E + T rather than E → T + E).

    Ambiguity example: the "dangling-else" grammar S → if E then S | if E then S else S | other is ambiguous because if E1 then if E2 then S1 else S2 has two parse trees (else attaches to the first or second if). The standard fix is to require that a "matched" statement appears between then and else, disambiguating else to attach to the nearest unmatched if.

    4.4 Top-Down Parsing

    Builds the parse tree from the root (start symbol) downward, constructing a leftmost derivation, expanding non-terminals to try to match the input; may require backtracking if a naive top-down parser guesses the wrong production.
    AspectTop-downBottom-up
    Tree builtRoot to leavesLeaves to root
    DerivationLeftmostRightmost, in reverse
    Typical techniqueRecursive descent, LLShift-reduce, LR
    Left recursionProblematicNot a problem

    4.5 Recursive Descent Parsing

    Each non-terminal becomes a procedure. The body of the procedure examines the current lookahead token to decide which production to apply, then calls procedures for the non-terminals on the right-hand side in order, matching terminals directly against the input.

    Grammar (after removing left recursion — see below): E → T E', E' → + T E' | ε, T → id.

    procedure E():
    T()
    Eprime()

procedure Eprime():
    if lookahead == '+':
        match('+')
        T()
        Eprime()
    else:
        return   # ε-production

procedure T():
    match('id')

    Full sample parse of id + id: E() → T() matches "id" → Eprime() sees '+' → match('+') → T() matches "id" → Eprime() sees end of input → returns (ε). Input fully consumed. Accepted.

    Left recursion problem: the original grammar E → E + T | T cannot be used for recursive descent, because the procedure for E would call itself immediately, with no token consumed first (E() calls E() calls E()...), causing infinite recursion. Left recursion is removed using the standard transformation:

    A → Aα | β        (original, left recursive)
    becomes
A  → β A'
A' → α A' | ε

    Applied to E → E + T | T: β = T, α = "+ T", giving E → T E', E' → + T E' | ε — exactly the grammar used above.

    4.6 Non-Recursive Predictive Parsing

    FIRST(α) rules:
    1. If α is a terminal a, FIRST(α) = {a}.
    2. If α is ε, FIRST(α) includes ε.
    3. If α is a non-terminal A with production A → Y1Y2...Yk, add FIRST(Y1) − {ε} to FIRST(A); if ε ∈ FIRST(Y1), also add FIRST(Y2) − {ε}, and so on; if ε ∈ FIRST(Yi) for all i, add ε to FIRST(A).
    FOLLOW(A) rules:
    1. Place $ in FOLLOW(start symbol).
    2. If A → αBβ, everything in FIRST(β) except ε is in FOLLOW(B).
    3. If A → αB, or A → αBβ where ε ∈ FIRST(β), then FOLLOW(A) ⊆ FOLLOW(B).

    4.8 LL Grammar

    "LL(1)" means: scan input Left-to-right, produce a Leftmost derivation, using 1 token of lookahead. A grammar is suitable for predictive (LL(1)) parsing when its parsing table has no multiply-defined entries, which requires:

    • No left recursion (direct or indirect) — remove it as shown in §4.5.
    • Left-factored — if two productions for the same non-terminal share a common prefix, they must be rewritten so the parser can decide with one token of lookahead.
    Left factoring: Original grammar → problem → transformed grammar → verification.
    Original: S → if E then S else S | if E then S — with lookahead "if", the parser cannot tell which alternative to take.
    Problem: both alternatives start with the same prefix "if E then S".
    Transformed: S → if E then S S', S' → else S | ε.
    Verification: now on seeing "if", only one production applies; the choice between the two original alternatives is deferred to S', which is decided by whether "else" follows — resolvable with one token of lookahead.

    4.9 Bottom-Up Parsing — Handles

    Handle: a substring that matches the right-hand side of a production, and whose reduction to the corresponding non-terminal represents one step along the reverse of a rightmost derivation.

    Handle pruning: repeatedly locate the handle in the current right sentential form and replace it by the corresponding non-terminal, until only the start symbol remains — this traces a rightmost derivation in reverse.

    Grammar: E → E + E | E * E | id. Rightmost derivation of id + id * id:

    E ⇒ E + E ⇒ E + E * E ⇒ E + E * id ⇒ E + id * id ⇒ id + id * id

    Right sentential formHandleReducing production

    E + EE + EE → E + E
    E—(start symbol reached)
    Each reduction shown reverses exactly one step of the rightmost derivation above (read bottom-to-top), confirming the handles are correctly identified.

    4.10 Shift-Reduce Parsing

    Uses a stack and a buffer of remaining input. Four possible actions: shift (push next input symbol onto the stack), reduce (replace a handle on top of the stack by the non-terminal on the left of the matching production), accept (stack contains just the start symbol and input is exhausted), error (no valid action applies).

    Full shift-reduce trace for id + id * id using E → E+E | E*E | id:

    StepStackInputAction
    1$id+id*id$shift
    2$id+id*id$reduce E→id
    3$E+id*id$shift
    4$E+id*id$shift
    5$E+id*id$reduce E→id
    6$E+E*id$shift (prefer shift: * binds tighter)
    7$E+E*id$shift
    8$E+E*id$reduce E→id
    9$E+E*E$reduce E→E*E
    10$E+E$reduce E→E+E
    11$E$accept

    Conflicts: at step 6, the parser could reduce E+E to E (using E→E+E) or shift the * — this is a genuine shift/reduce conflict, resolved here by the convention that * has higher precedence, so shift is chosen. A reduce/reduce conflict arises instead when two different productions could both be used to reduce the same handle (e.g. if a grammar had both A → id and B → id reducible in the same context) — the parser cannot decide which non-terminal to reduce to without extra information.

    4.11 LR Parsers

    "LR(k)" parses Left-to-right, builds a Rightmost derivation in reverse, with k symbols of lookahead. This guide constructs an SLR(1) table (LR(0) items plus FOLLOW sets), the standard entry point for LR parsing taught alongside LL methods, and clearly separates it from plain LR(0) and from CLR(1)/LALR(1).
    Procedure:
    1. Augment the grammar: add S' → S.
    2. Construct the canonical collection of LR(0) items using closure and goto.
    3. Build states (item sets) from the collection.
    4. Fill ACTION using: shift on states with an item A→α·aβ; reduce on items A→α· using FOLLOW(A) (this is the SLR rule); accept on S'→S·.
    5. Fill GOTO using goto on non-terminals.
    6. Simulate the parse of a string using the ACTION/GOTO table.

    Chapter 5 — Semantic Analysis

    5.1 Syntax-Directed Definitions (SDDs)

    An SDD associates one or more attributes with each grammar symbol and one or more semantic rules with each production, describing how attributes are computed.
    ProductionSemantic rule
    E → E1 + TE.val = E1.val + T.val
    E → TE.val = T.val
    T → numT.val = num.lexval

    Syntax tree vs parse tree: a parse tree shows every grammar symbol used in the derivation (including ones introduced purely for grammar structure); a syntax tree (abstract syntax tree) omits such structural detail and keeps only the operators and operands that matter semantically, e.g. 3 + 4 is a parse tree with several nested non-terminal nodes but a syntax tree with just one "+" node and two leaf children 3 and 4.

    5.2 Synthesized and Inherited Attributes

    SynthesizedInherited

    5.3 Dependency Graph

    A dependency graph has one node per attribute instance; an edge from attribute a to attribute b means a must be evaluated before b (b depends on a). A topological sort of this graph gives a valid evaluation order.

    Grammar with rules: D → T L, {L.in = T.type}; L → L1 id, {L1.in = L.in; addtype(id.entry, L.in)}; L → id, {addtype(id.entry, L.in)}.

    For input real p, q (i.e. T L where L = L1 id(q), L1 = id(p)):

    T.type --------> L.in --------> L1.in --------> addtype(p, L1.in)
                                  |
                                  +--------------> addtype(q, L.in)

    Valid evaluation order: T.type, then L.in, then L1.in, then addtype(p,...), then addtype(q,...) (order among the two addtype calls does not matter since neither depends on the other, but both must follow the "in" attribute they use). This ordering is valid because every edge in the graph points from an earlier node to a later one — no node is used before it is computed.

    5.4 S-Attributed Definitions

    An SDD is S-attributed if every attribute is synthesized. S-attributed SDDs can be evaluated during a single bottom-up (e.g. LR) parse, since a synthesized attribute at a node can be computed as soon as all its children have been reduced — this fits naturally with a shift-reduce parser's stack, which can carry attribute values alongside grammar symbols.
    The postfix-translation example of §2.2 (E.t = E1.t||T.t||'+') is S-attributed: E.t depends only on the values of its children.

    5.5 L-Attributed Definitions

    An SDD is L-attributed if, for every production A → X1X2...Xn, each inherited attribute of Xi depends only on: (a) inherited attributes of A, and (b) attributes (synthesized or inherited) of X1,...,Xi-1 (symbols to its left) — never on attributes of Xi+1,...,Xn or on Xi's own synthesized attributes feeding back inward. This restriction allows evaluation during a single left-to-right (e.g. top-down / recursive-descent) traversal.

    S-attributed vs L-attributed: every S-attributed SDD is automatically L-attributed (since synthesized attributes trivially satisfy the "depends only on the left / on the parent" rule — they don't use inherited attributes at all), but not every L-attributed SDD is S-attributed, because L-attributed SDDs may also use inherited attributes, as long as they only look leftward and upward. It is incorrect to claim that every SDD using inherited attributes is automatically L-attributed — an inherited attribute that depends on a sibling to its right violates the L-attributed restriction.

    The type-declaration example in §5.3 (L.in passed from parent T.type, then rightward down the list L1.in = L.in) is L-attributed: each inherited attribute depends only on the parent or on symbols to the left, never on a symbol to the right.

    5.6 Top-Down and Bottom-Up Evaluation

    Evaluation order must respect the dependency graph. S-attributed definitions naturally match bottom-up parsers (each reduction computes the synthesized attribute immediately). L-attributed definitions naturally match top-down / left-to-right traversal (recursive descent can pass inherited attributes as procedure parameters and return synthesized attributes as results). Choosing the wrong evaluation strategy for a given SDD (e.g. trying to evaluate a definition with rightward-dependent inherited attributes during a strict left-to-right single pass) leads to using an attribute before it is computed.

    Type
    A set of values together with operations defined on them.
    Type system
    The collection of rules assigning types to program constructs and checking their consistency.
    Type expression

    Type rule
    A rule specifying the type of a construct given the types of its parts, e.g. "if E1 has type int and E2 has type int, then E1+E2 has type int".

    Static typing checks types at compile time; dynamic typing checks (some) types at run time. Compiler-level type checking, as covered here, refers primarily to static checking performed during semantic analysis.

    Chapter 6 — Intermediate Code

    6.1 Intermediate Languages

    An intermediate representation (IR) sits between the source language and the target machine. Advantages: a compiler can be retargeted to a new machine by writing only a new back end; machine-independent optimizations can be written once and reused for every target; the front end and back end can be developed/tested somewhat independently.

    6.2 Three-Address Code (TAC)

    Standard forms: x = y op z, x = op y, x = y, if x relop y goto L, goto L, plus labels and procedure-call instructions. Each instruction has at most one operator on the right, so complex expressions are broken into a sequence using temporaries.

    Worked example — x = (a + b) * (c - d)

    1. Parse respecting precedence: (a+b) and (c-d) computed first, then multiplied.
    2. Introduce temporaries and generate line by line:
    t1 = a + b
t2 = c - d
t3 = t1 * t2
x  = t3
    Verification: with a=5,b=3,c=8,d=2 → t1=8, t2=6, t3=48, x=48; direct evaluation (5+3)*(8-2)=8*6=48. ✔

    6.3 Declarations

    Declarations are usually not translated into executable TAC but instead update the symbol table with type and (as computed) storage offset. E.g. for int a; float b; the compiler records a: type=int, offset=0, width=4; b: type=float, offset=4, width=4 — no TAC instructions are emitted for the declarations themselves.

    6.4 Assignment Statements

    x = a * (b + c) - d →

    t1 = b + c
t2 = a * t1
t3 = t2 - d
x  = t3

    6.5 Addressing Array Elements

    One-dimensional array, index range starting at low, element width w, base address base:

    address(A[i]) = base(A) + (i - low) × w

    Two-dimensional array A[low1..high1][low2..high2], row-major storage, element width w, with n2 = number of columns = high2 - low2 + 1:

    address(A[i][j]) = base(A) + ((i - low1) × n2 + (j - low2)) × w

    Numerical example 1 (1-D): array A[0..9] of int (w = 4 bytes), base(A) = 1000. Find address of A[6].

    address(A[6]) = 1000 + (6 - 0) × 4 = 1000 + 24 = 1024
    Verification: elements 0..5 occupy 6×4=24 bytes before A[6], so A[6] starts at 1000+24=1024. ✔

    Numerical example 2 (2-D): array B[0..2][0..3] of int (w=4), base(B)=2000, row-major, n2 = 4-0 = 4. Find address of B[1][2].

    address(B[1][2]) = 2000 + ((1-0)×4 + (2-0)) × 4 = 2000 + (4+2)×4 = 2000 + 24 = 2024
    Verification: row 0 (4 elements) fully precedes row 1, plus 2 more elements within row 1: (4+2)=6 elements × 4 bytes = 24; 2000+24=2024. ✔

    Corresponding TAC for x = B[i][j] (with i,j variables, n2=4, w=4):

    t1 = i * 4
t2 = t1 + j
t3 = t2 * 4
t4 = base(B) + t3    // could also be written as: t4 = t3 + base_B  (address computation)
x  = t4  [with an indirect load, i.e. x = *t4 in practice]

    6.6 Boolean Expressions

    Two representations are common: (a) numeric — compute a 0/1 value; (b) flow-of-control (jumping code) — the value of a boolean expression is represented by a position reached in the code (true-branch vs false-branch), using short-circuit evaluation for && and ||. The jumping-code representation is used below.

    Worked example — if (a < b && c != d) x = 1; else x = 0; using short-circuit control flow:

          if a < b goto L1
      goto Lfalse
L1:   if c != d goto Ltrue
      goto Lfalse
Ltrue:  x = 1
        goto Lnext
Lfalse: x = 0
Lnext:

    This uses jumps rather than computing an intermediate 0/1 boolean temporary, consistent with a jumping-code (backpatch-oriented) representation: the first condition, if false, short-circuits directly to Lfalse without ever testing the second condition.

    6.7 Case Statements

    switch (x) { case 1: S1; case 2: S2; default: S3; } translated using a comparison chain:

          t = x
      if t == 1 goto L1
      if t == 2 goto L2
      goto Ldefault
L1:   <code for S1>
      goto Lexit
L2:   <code for S2>
      goto Lexit
Ldefault: <code for S3>
Lexit:

    (An alternative implementation strategy for many cases with dense values is a jump table indexed directly by the case value, avoiding the linear comparison chain; mentioned here as an alternative optimization, not the base translation.)

    6.8 Procedure Calls

    call p(a, b) translated as a sequence of param instructions followed by a call:

    param a
param b
call p, 2      // 2 = number of parameters

    If p returns a value: x = call p, 2 stores the return value into x. The return instruction inside p's body (e.g. return t1) passes the value back to the caller.

    6.9 Backpatching

    Backpatching avoids a separate pass over the syntax tree by generating jump instructions with the target left temporarily empty, collecting each such instruction's location into a list, and later filling in ("backpatching") the correct label once it becomes known.

    Core operations:
    • truelist(n) — list of jumps to be targeted where control should go if n is true.
    • falselist(n) — list of jumps to be targeted where control should go if n is false.
    • nextlist(n) — list of jumps to be targeted at the instruction following statement n.
    • makelist(i) — create a new list containing only index i.
    • merge(p1, p2) — concatenate two lists.
    • backpatch(list, target) — insert target as the jump destination of every instruction in list.

    Worked example — if (a < b) then S1 else S2

    1. Generate code for condition a < b: 
      100: if a < b goto _     (target unknown yet)
101: goto _              (target unknown yet)
      truelist = {100}, falselist = {101}.
    2. Backpatch truelist to the instruction that begins S1 (say instruction 102): backpatch({100}, 102).
    3. Generate S1's code (say instructions 102–104), then generate an unconditional jump (105: goto _) to skip S2; add 105 to a new nextlist.
    4. Backpatch falselist to the instruction that begins S2 (say instruction 106): backpatch({101}, 106).
    5. Generate S2's code (106–108).
    6. Backpatch the S1-exit jump's list ({105}) to the instruction after S2 (109): backpatch({105}, 109).

    Final backpatched TAC:

    100: if a < b goto 102
101: goto 106
102: 
105: goto 109
106: 
109:
    Verification: every jump target listed above (102, 106, 109) is a real instruction address filled in only after it became known, and tracing execution for a<b true goes 100→102→(S1)→105→109 (skipping S2), while a<b false goes 100→101→106→(S2)→109 — exactly the intended if-then-else control flow. ✔

    While-loop sketch using the same machinery: while (E) S → label the test, backpatch E's truelist to S's first instruction, backpatch E's falselist to the instruction after the loop, and after S generate a jump back to the test label (no backpatch needed there since the target — the test label — is already known).

    Chapter 7 — Code Generation and Optimizing

    7.1 Code Generator Design Issues

    • Input: intermediate representation (e.g. TAC), plus symbol-table information.
    • Target code: assembly or relocatable machine code.
    • Instruction selection: choosing which machine instruction(s) implement each IR operation; naive selection can produce redundant instructions.
    • Register allocation: deciding which values are kept in registers (limited, fast) vs memory.
    • Register assignment: deciding exactly which physical register holds a chosen value.
    • Evaluation order: the order operations are performed can affect the number of registers needed.
    • Addressing modes, instruction cost, machine constraints: the code generator must respect the specific target machine's instruction set and cost model.

    7.2 Target Machine

    Assumed abstract target machine for the worked examples below:

    • Registers: R0, R1, R2, ... (general purpose)
    • Instructions: MOV src,dst; ADD src,dst (dst=dst+src); SUB, MUL similarly; ST src,mem (store)
    • Addressing modes: register, memory direct
    • Cost: 1 unit per instruction (simplified)

    7.6 Simple Code Generator

    Maintains, for each register, a register descriptor (which variable(s) it currently holds) and for each variable an address descriptor (where its current value(s) can be found: register, memory, or both). For x = y op z: pick a register for the result (reusing one already holding y if possible and if y is not needed later), load operands not already in registers, emit the operation, update descriptors, and store to memory only if required (e.g. at end of block, or if the register is needed for something else and the value is still live).

    Worked example — TAC:

    t1 = a + b
t2 = t1 * c
d  = t2
    1. t1 = a + b: load a into R0 (MOV a,R0), add b (ADD b,R0) → R0 holds t1. Register descriptor: R0={t1}. Address descriptor: t1={R0}.
    2. t2 = t1 * c: t1 already in R0, so multiply in place (MUL c,R0) → R0 now holds t2 (t1 is dead after this use). Register descriptor: R0={t2}. Address descriptor: t2={R0}.
    3. d = t2: t2 already in R0, so store directly (ST R0,d).

    Final target code:

    MOV a,R0
ADD b,R0
MUL c,R0
ST  R0,d
    Verification: with a=2,b=3,c=4 → R0=2, R0=5, R0=20, d=20; TAC computation gives t1=5, t2=20, d=20 — identical. Only one register was needed because t1 became dead immediately after producing t2, illustrating why next-use information (§7.5) is essential for good register allocation. ✔

    7.7 Introduction to Code Optimization (supporting material)

    Code optimization means transforming intermediate or target code to use less time and/or space while preserving the program's meaning; it typically operates on the flow graph built in §7.4, using data such as the next-use information of §7.5. The syllabus item list for this chapter ends at "Simple code generator"; the specific optimization techniques below are included only as supporting material, clearly separate from the examinable core:

    • Constant folding — evaluate constant expressions at compile time, e.g. t1 = 2 * 3 → t1 = 6.
    • Constant propagation — substitute a variable's known constant value at its uses.
    • Common subexpression elimination — reuse a previously computed value instead of recomputing an identical expression.
    • Dead-code elimination — remove computations whose results are never used (no next use, ever).
    • Strength reduction — replace an expensive operation with a cheaper equivalent, e.g. x * 2 → x + x.
    • Peephole optimization — examine a small sliding window of generated instructions and replace inefficient patterns, e.g. MOV R0,R1 / MOV R1,R0 → remove the redundant second move.

    Context-free grammar: a grammar whose productions have a single non-terminal on the left.
    Terminal
    A basic (indivisible) symbol of the language, i.e. a token.
    Non-terminal
    A syntactic variable used to define grammar structure.
    Derivation
    A sequence of production applications from the start symbol.
    Parse tree
    Tree representation of a derivation showing every grammar symbol involved.
    Syntax tree
    A condensed tree keeping only semantically significant structure.
    Semantic analysis
    The phase checking meaning-related rules (types, scope) beyond pure syntax.
    Attribute
    A value associated with a grammar symbol occurrence, computed by a semantic rule.
    Synthesized attribute
    Attribute computed from children's attributes (bottom-up flow).
    Inherited attribute
    Attribute computed from parent's/siblings' attributes (top-down/lateral flow).
    Dependency graph
    Graph of attribute instances showing which must be evaluated before which.
    Type expression
    A notation denoting a type.
    Type equivalence
    The rule for deciding whether two type expressions denote the same type (structural or name).
    NFA
    Nondeterministic finite automaton — allows multiple/no transitions per symbol and ε-moves.
    DFA
    Deterministic finite automaton — exactly one transition per state/symbol pair.
    ε-closure
    Set of states reachable using only ε-transitions.
    Thompson construction
    Algorithm building an NFA directly from a regular expression.
    Subset construction
    Algorithm converting an NFA into an equivalent DFA using sets of NFA states as DFA states.
    FIRST
    Set of terminals (and possibly ε) that can begin strings derived from a grammar symbol/sequence.
    FOLLOW
    Set of terminals that can immediately follow a non-terminal in some sentential form.
    LL
    Top-down parsing: Left-to-right scan, Leftmost derivation.
    LR
    Bottom-up parsing: Left-to-right scan, Rightmost derivation (in reverse).
    Handle
    A substring matching a production's right side, reducible in a step of the reverse rightmost derivation.
    Shift
    Push the next input symbol onto the parsing stack.
    Reduce
    Replace a handle on the stack by the corresponding non-terminal.
    Accept
    Parsing action confirming the whole input is a valid sentence of the grammar.
    Conflict
    A parsing-table cell needing more than one action (shift/reduce or reduce/reduce).
    Three-address code
    IR form with at most one operator per instruction.
    Temporary
    A compiler-generated variable holding an intermediate value.
    Label
    A named position in the code, used as a jump target.
    Backpatching
    Technique of leaving jump targets blank and filling them in once known.
    Basic block
    Maximal straight-line code sequence with one entry and one exit.
    Leader
    First statement of a basic block, identified by the leader rules.
    Flow graph
    Graph of basic blocks showing possible control-flow transfers.
    Live variable
    A variable whose current value may still be used later in the program.
    Next use
    The next statement at which a variable's current value will be used.
    Register descriptor
    Tracks which variable(s) a register currently holds.
    Address descriptor
    Tracks where a variable's current value(s) can be found.
    Target machine
    The machine (real or abstract) for which code is being generated.
    Activation record
    Runtime data structure (stack frame) holding a procedure call's local state.

    How To Solve Compiler Design Problems — Exam Checklists

    RE → NFA (Thompson)
    1. Parse the RE into its structure (union, concatenation, star) respecting precedence.
    2. Build a fragment for each symbol.
    3. Combine fragments bottom-up using the four construction rules.
    4. Number all states once combined.
    5. Trace 1–2 sample strings to verify.
    NFA → DFA (subset construction)
    1. Compute ε-closure of the NFA start state → DFA start state.
    2. For each DFA state and symbol, compute move then ε-closure.
    3. Add any new state set found; repeat until no new sets appear.
    4. Mark accepting DFA states (contain an NFA accepting state).
    5. Verify with sample strings.
    FIRST
    1. Terminal → FIRST = itself.
    2. ε-production → add ε.
    3. For A→Y1...Yk, add FIRST(Y1)-{ε}; if ε∈FIRST(Y1) continue to Y2, etc.
    4. If all Yi can derive ε, add ε to FIRST(A).
    FOLLOW
    1. $ ∈ FOLLOW(start symbol).
    2. A→αBβ: add FIRST(β)-{ε} to FOLLOW(B).
    3. A→αB or ε∈FIRST(β): add FOLLOW(A) to FOLLOW(B).
    4. Iterate until no changes.
    LL(1) parsing table & predictive parsing
    1. Compute FIRST, FOLLOW for all non-terminals.
    2. For each production, place it in row A, column a for each a in FIRST(rhs); if ε in FIRST(rhs), also place in columns of FOLLOW(A).
    3. Check for conflicts (LL(1)?).
    4. Simulate stack + input using the table; shift/expand until $/$ match → accept.
    Recursive descent
    1. Remove left recursion and left factor the grammar.
    2. Write one procedure per non-terminal.
    3. In each, branch on the lookahead to choose the production, then call procedures/match terminals in order.
    4. Trace the procedure calls against the input to verify.
    Handle pruning / shift-reduce
    1. Maintain a stack and remaining input.
    2. At each step: shift if no complete handle is on top, else reduce the handle using the matching production.
    3. Resolve shift/reduce conflicts by declared precedence/associativity.
    4. Accept when stack = start symbol and input is empty.
    LR (SLR) parsing
    1. Augment the grammar.
    2. Build item sets via closure and goto from the augmented start item.
    3. Fill ACTION (shift/reduce/accept) and GOTO tables (reduce entries placed using FOLLOW for SLR).
    4. Simulate the parse using the table; check for conflicts.
    Syntax-directed evaluation
    1. List every attribute and its semantic rule per production.
    2. Classify each attribute as synthesized or inherited.
    3. Build the dependency graph for the specific input.
    4. Topologically order and evaluate.
    Type checking
    1. List declared types via the symbol table.
    2. Apply type rules bottom-up on the expression tree.
    3. Insert conversions per the language's coercion rules.
    4. Flag any rule violation as a type error.
    TAC generation
    1. Respect operator precedence/associativity when structuring the expression.
    2. Introduce a temporary per operator application, innermost first.
    3. Write one instruction per operator.
    4. Verify by substituting sample values.
    Array addressing
    1. Identify base address, element width, index bounds.
    2. 1-D: base + (i-low)×w. 2-D row-major: base + ((i-low1)×n2 + (j-low2))×w.
    3. Substitute numbers and compute.
    4. Verify by counting elements manually.
    Boolean/control translation
    1. Decide jumping-code representation (true/false destinations).
    2. Apply short-circuit rules for && / ||.
    3. Generate incomplete jumps with truelist/falselist.
    4. Backpatch once targets are known.
    Case/switch translation
    1. Evaluate the selector into a temporary.
    2. Generate a comparison + conditional jump per case label.
    3. Add a default fallthrough and an exit label.
    4. Backpatch each label once the corresponding code position is known.
    Backpatching
    1. Generate jumps with blank targets; collect their indices into truelist/falselist/nextlist.
    2. Use makelist/merge to combine lists as needed.
    3. Once the target instruction's address is known, call backpatch(list, target).
    4. Verify every jump address in the final code is filled in and correct.
    Basic blocks & flow graphs
    1. Number every TAC statement.
    2. Apply the three leader rules.
    3. Group statements between consecutive leaders into blocks.
    4. Draw edges for fall-through and jump targets.
    Next-use information
    1. Scan the block backward, statement by statement.
    2. At x=y op z: record x's info, then mark x dead/no-next-use, then set y,z live with next-use = this statement.
    3. Carry information upward to the start of the block.
    Simple code generation
    1. For each TAC instruction, choose/reuse a register for the result using next-use info.
    2. Load any operand not already in a register.
    3. Emit the operation; update register/address descriptors.
    4. Store to memory only when required (end of block or register reuse forces it).

    Common Exam Traps

    Confusing token (the abstract category) with the lexeme (the actual matched text) — e.g. writing "id" as the lexeme instead of the identifier's spelling.
    NFA vs DFA confusion — assuming an NFA table can have only one entry per cell like a DFA; NFAs may have zero, one, or several transitions (plus ε-moves).
    Computing an incorrect ε-closure — forgetting that ε-closure(s) always includes s itself, or missing a chain of multiple ε-transitions.
    Missing subset-construction states — stopping before every reachable DFA state set has been generated and its transitions computed.
    Incorrect FIRST/FOLLOW — forgetting to propagate FIRST(β) into FOLLOW(B) when a symbol can derive ε, or forgetting $ ∈ FOLLOW(start symbol).
    Incorrect LL(1) table entries — placing a production only under FIRST and forgetting the FOLLOW-based entries required when the production derives ε.
    Left recursion in recursive descent — attempting to hand-write a recursive-descent procedure directly from a left-recursive grammar, causing infinite recursion.
    Incorrectly identifying the handle — choosing a substring that matches a production's RHS syntactically but does not correspond to the correct step of the rightmost derivation in reverse.
    Shift/reduce confusion — reducing too early (before the true handle is fully on the stack) or shifting when a valid reduction is required.
    Incorrect LR item closure — forgetting to add closure items for every non-terminal immediately after a dot.
    Wrong LR reduction — reducing using a production whose RHS does not match the actual symbols on top of the stack.
    Synthesized/inherited confusion — labeling an attribute that depends on parent/sibling information as synthesized, or vice versa.
    Invalid attribute dependency order — evaluating an attribute before all attributes it depends on (per the dependency graph) have been computed.
    Structural/name equivalence confusion — assuming two types with the same structure but different names are always equivalent (true only under structural equivalence, not name equivalence).
    Incorrect type conversion — inserting a narrowing conversion silently where the language requires an explicit cast, or vice versa.
    Wrong TAC precedence — generating temporaries in an order that ignores operator precedence or associativity, changing the computed result.
    Incorrect array-address formula — forgetting to subtract the lower bound, or using column-major arithmetic when the array is row-major (or vice versa).
    Wrong Boolean jump logic — failing to implement short-circuit evaluation correctly, e.g. still evaluating the second operand of && after the first is false.
    Incorrect case labels — mismatching comparison values against case constants, or omitting the default/exit label.
    Broken backpatch lists — backpatching a list to the wrong target instruction, or forgetting to merge lists (e.g. nextlist of two branches) before backpatching them together.
    Incorrect leader identification — forgetting that the statement immediately after a jump is also a leader (rule 3), causing blocks to be merged incorrectly.
    Incorrect flow-graph edges — omitting a fall-through edge, or adding an edge that does not correspond to any actual jump or fall-through in the code.
    Incorrect next-use scanning — scanning forward instead of backward, which gives no valid way to determine "next" use.
    Poor register choice — evicting a register still holding a live value with a future next-use, forcing an unnecessary reload/store.
    Generated code that changes the original computation — e.g. reordering non-commutative operations (like subtraction) incorrectly during optimization or code generation.

    5. Parsing Cheat Sheet

    • LL(1): table filled from FIRST (and FOLLOW when ε is derivable); stack-based simulation matching terminals and expanding non-terminals.
    • SLR(1): closure + goto build item sets; reduce entries placed using FOLLOW of the reduced non-terminal.
    • Shift-reduce: shift when no handle is ready; reduce when the top of the stack matches a production's RHS.

    6. Automata Cheat Sheet

    • Thompson: symbol, concatenation (ε-link accept→start), union (new start/accept with ε-branches), star (new start/accept with loop-back ε-edges).
    • Subset construction: DFA states = ε-closures of NFA state sets reached via move(); repeat until closed under all input symbols.

    7. TAC / Backpatching Cheat Sheet

    • Introduce one temporary per operator, respecting precedence/associativity.
    • truelist/falselist/nextlist hold indices of jumps awaiting a target.
    • backpatch(list, target) fills in every jump in the list with the given target address.

    8. Code Generation Cheat Sheet

    • Reuse a register already holding an operand when possible (checked via next-use info).
    • Update register/address descriptors after every instruction.
    • Store to memory only when the value is still live and its register must be reused, or at block exit.

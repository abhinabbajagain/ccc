    Chapter 1: Overview of System Analysis and Design

    1.1 Introduction to System Analysis and Design

    System: A set of interrelated components working together toward a common goal, exchanging inputs, processes, and outputs, bounded by an environment.
    System Analysis: The process of studying an existing business/system situation to identify its problems and requirements, and defining what a new or improved system must do to meet those requirements.
    System Design: The process of specifying how the requirements identified during analysis will be technically implemented — architecture, data structures, interfaces, modules, and controls.
    System Analysis and Design (SAD): A structured discipline/methodology combining analysis and design activities to build information systems that solve organizational problems efficiently, accurately, and on schedule.
    AspectSystem AnalysisSystem Design
    Core questionWhat should the system do?How will the system do it?
    FocusBusiness requirements, logical modelTechnical/physical implementation
    OutputRequirement specification, DFD, ERDStructure chart, DB schema, UI/forms design
    Performed bySystem analyst (with users)System analyst/designer (with developers)
    OrientationProblem-orientedSolution-oriented

    Objectives/Purpose of SAD

    • Understand and document current system problems and information needs.
    • Define accurate, complete, and validated requirements.
    • Design an efficient, maintainable, cost-effective solution.
    • Bridge the gap between user needs and technical implementation.
    • Reduce risk of project failure through structured, phased development.
    Example: For a library wanting to computerize book issue — Analysis finds out that "a member should be able to reserve a book and get notified when it is available." Design decides the reservation table structure, the notification trigger, and the screen the librarian uses.

    1.2 Information Systems and Their Types

    Information System (IS): An organized combination of people, hardware, software, communication networks, data resources, and procedures that collects, transforms, and disseminates information in an organization.

    Components of an IS

    • People — end users, IS staff
    • Hardware — machines, media
    • Software — programs, procedures
    • Data — facts stored for processing
    • Network/Communication — connects resources

    Purpose

    To support daily operations, managerial decision-making, and strategic planning through timely and accurate information.

    TypeDefinitionPurposeCharacteristicsExample
    TPS (Transaction Processing System)Processes routine, day-to-day business transactionsOperational efficiencyHigh volume, repetitive, real-time/batchBank deposit/withdrawal system
    MIS (Management Information System)Converts TPS data into summarized reports for managersTactical/managerial decisionsPeriodic structured reportsMonthly sales-summary system
    DSS (Decision Support System)Supports semi-structured/unstructured decision-making with modelsAnalytical "what-if" decisionsInteractive, model-drivenRoute/investment optimization system
    EIS (Executive Information System)Gives top executives quick access to key internal/external indicatorsStrategic decisionsDrill-down, dashboards, summarizedCEO dashboard of company KPIs
    ES/KWS (Expert/Knowledge System)Mimics human expert reasoning using a knowledge base & rulesSpecialized problem-solvingRule-based inference engineMedical diagnosis support system

    General trend: TPS → MIS → DSS → EIS represents increasing management level (operational → strategic) and decreasing data volume/structure.

    1.3 Stakeholders of Information Systems

    Stakeholder: Any person or group who has an interest in, is affected by, or can affect the outcome of a system project.

    Stakeholders matter because unaddressed needs of any group can cause requirement gaps, resistance to change, or project failure.

    CategoryRole/InterestExample
    System OwnersFund the project, set priorities, care about cost/ROISenior management, sponsors
    System UsersUse the system daily; care about ease of use, correctnessClerks, cashiers, librarians
    System Analysts/DesignersStudy needs, translate requirements into designBusiness/system analyst
    System BuildersConstruct/code and technically implement the systemProgrammers, DBAs
    External StakeholdersIndirectly affected/interested outside the organizationVendors, regulators, customers

    1.4 Systems Development Life Cycle (SDLC) & Life-Cycle Models

    SDLC: A structured, phased approach describing the stages an information system passes through from initial idea to retirement.

    Purpose: Provides a disciplined framework to control scope, cost, quality and time; ensures requirements are met and nothing is skipped.

    PhaseKey ActivitiesDeliverable
    1. Preliminary Investigation / PlanningIdentify problem, scope, feasibilityFeasibility report
    2. Requirement/Systems AnalysisGather & document requirements, model current systemRequirement spec., DFD/ERD
    3. Systems DesignDesign architecture, DB, I/O, modulesDesign specification
    4. Implementation/DevelopmentCode, build, unit testWorking modules/programs
    5. TestingIntegration/system/UAT testingTest reports
    6. Installation/DeploymentConvert & go live (see Ch.8 strategies)Operational system
    7. MaintenanceFix, adapt, enhance, preventUpdated system, change logs

    Life-Cycle Models

    ModelMeaningPhases/FlowAdvantagesDisadvantagesSuitable When
    WaterfallSequential, one phase finished before next startsLinear: Plan→Analyze→Design→Build→Test→Deploy→MaintainSimple, disciplined, easy to manage/documentRigid, late testing, hard to accommodate changeRequirements are clear & stable
    IncrementalSystem built and delivered in usable incrementsRepeated mini-waterfalls, each adding featuresEarly partial delivery, easier to manage riskNeeds good architecture up frontRequirements known but can be phased
    Iterative/PrototypingBuild a working model early, refine through feedbackQuick design→prototype→user review→refine (repeat)Clarifies unclear requirements, high user involvementScope creep, can be discarded/costlyRequirements unclear or evolving
    SpiralCombines iterative development with explicit risk analysisRepeated loops: Plan→Risk analysis→Engineer→EvaluateStrong risk management, good for large systemsComplex, costly, needs risk-assessment expertiseLarge, high-risk, long-duration projects
    AgileAdaptive, incremental delivery via short iterations (sprints)Repeated short cycles with continuous user feedbackFlexible, fast delivery, responsive to changeNeeds disciplined team, less predictable long-term planRequirements likely to change; small/co-located teams

    Chapter 2: Process and Conceptual Modeling

    2.1 The System Analyst

    System Analyst: A professional who studies an organization's problems and needs, determines how people, methods, and technology can best solve them, and designs the corresponding system.
    AspectDetails
    RolesInvestigator, problem-solver, mediator, project manager, technical writer
    ResponsibilitiesRequirement gathering, modeling (DFD/ERD/UML), feasibility study, documentation, liaison between users & developers, testing support
    SkillsAnalytical/logical thinking, communication, technical knowledge, business knowledge, interpersonal & management skills
    Relationship with usersElicits requirements, validates understanding, manages expectations
    Relationship with managementReports feasibility/progress, seeks approval & resources
    Relationship with developersHands off specifications, clarifies design intent during build

    2.2 Introduction to Data Flow Diagrams (DFD)

    DFD: A graphical tool that represents the flow of data through a system — showing processes, data stores, external entities, and the data flows connecting them — without depicting control logic or timing.

    Purpose/Importance: Communicates system data flow to both technical and non-technical stakeholders; forms the basis for the data dictionary and later program/module design.

    SymbolMeaningNaming Rule
    External EntitySource/destination of data outside system boundaryNoun (e.g., "Customer", "Supplier")
    ProcessTransforms input data into output dataVerb + noun (e.g., "Validate Order")
    Data FlowMovement of data between componentsNoun describing the data (e.g., "Order Details")
    Data StoreRepository where data is held (file/table)Noun (e.g., "Student File")

    2.3 Concepts Used in Drawing DFDs

    • Data flow direction: Arrows show direction only; a two-way exchange needs two separate arrows or two labeled flows.
    • Process naming: Verb-noun phrase; never name a process after a person/department.
    • Balancing: Every child-level diagram's inputs/outputs must exactly match its parent process's inputs/outputs — no new or missing flows.
    • Leveling: Progressive decomposition — Context (Level 0/Diagram 0 boundary) → Level 0 → Level 1 → Level 2, each showing more detail.
    • Numbering: Processes numbered hierarchically (1, 1.1, 1.2, 1.2.1 …) reflecting the decomposition tree.
    • Valid/invalid flows: Data cannot flow directly Entity→Store, Store→Entity, Store→Store, or Entity→Entity — it must always pass through a process.
    • Logical consistency: A process must have at least one input and one output; a data store must be both written to and read from somewhere in the model.
    Common DFD mistakes: Data flow directly between two stores/two entities; a "black-hole" process (input, no output) or "miracle" process (output, no input); unbalanced levels; using control flow/logic instead of data flow; naming a process with a noun only.

    2.4 DFD Design (up to Level 2) — Worked Example: Library Book-Issue System

    Problem statement: A library wants a system where a Member requests to borrow/return a book; the system checks availability, records the transaction, updates the catalog, and calculates fines for late returns. A Librarian manages the catalog.

    1. External entities: Member, Librarian
    2. Processes: 1 Issue Book, 2 Return Book, 3 Maintain Catalog
    3. Data flows: Book Request, Book Details, Return Details, Fine Receipt, Catalog Update, Availability Status
    4. Data stores: D1 Book File, D2 Transaction File

    Level 1 decomposition of Process 1 (Issue Book): 1.1 Check Availability (reads D1) → 1.2 Verify Member Eligibility → 1.3 Record Transaction (writes D2) → 1.4 Update Book Status (writes D1). Inputs/outputs of 1.1–1.4 combined must equal the inputs/outputs shown for process 1 in Level 0 (this is balancing).

    Level 2 decomposition of 1.1 (Check Availability): 1.1.1 Search Catalog by Title/ID → 1.1.2 Check Copies Available → 1.1.3 Return Availability Status to Member. Again, combined inputs/outputs equal process 1.1's inputs/outputs — balancing preserved down every level.

    Exam tip: Always state explicitly, in words, why your diagrams are balanced — examiners award marks for stating "sum of child inputs/outputs = parent inputs/outputs."

    2.5 Conceptual Modeling

    Conceptual Model: A high-level, technology-independent representation of the data and relationships in a system, focused on business meaning rather than storage details.
    Conceptual ModelPhysical Model
    Business-oriented, technology-independentTechnology-specific (tables, indexes, datatypes)
    Shows entities and relationshipsShows tables, columns, keys, constraints
    Used during analysisUsed during design/implementation

    Conceptual modeling (ER modeling) feeds directly into database design: entities become tables, attributes become columns, relationships become foreign keys.

    2.6 Entity Relationship Diagrams (ERD)

    ER Model: A conceptual data model that describes data as entities, attributes, and relationships between entities.
    TermMeaningExample
    EntityA real-world object/concept about which data is storedStudent
    AttributeA property/characteristic of an entityName, Roll No.
    Entity SetCollection of entities of the same typeAll Students
    RelationshipAn association between two or more entitiesStudent Enrolls in Course
    Relationship SetCollection of relationships of same typeAll Enrolls-in links
    Primary KeyAttribute(s) uniquely identifying each entity instanceRoll No.
    Candidate KeyAny attribute qualified to be a primary keyRoll No. or Email
    Composite AttributeAn attribute divisible into sub-partsAddress → Street, City
    Multivalued AttributeAttribute that can hold multiple valuesPhone Numbers
    Derived AttributeValue computed from other attributesAge from Date of Birth

    Cardinality & ERD Notation

    TypeMeaningExample
    1:1One instance of A relates to exactly one of BEmployee — Parking Slot
    1:MOne instance of A relates to many of BDepartment — Employees
    M:NMany instances of A relate to many of BStudent — Course

    Participation: Total (double line — every entity instance must participate) vs Partial (single line — participation optional).

    Identifying components (worked steps): 1) Read problem statement, underline nouns → candidate entities (Student, Course). 2) Underline verbs connecting nouns → relationship (Enrolls). 3) List properties of each noun → attributes. 4) Decide which attribute uniquely identifies each entity → primary key. 5) Determine how many instances of one relate to the other → cardinality.

    Common ERD mistakes: Treating an attribute as an entity (e.g., making "Address" its own entity without justification); missing primary keys; assigning wrong cardinality (e.g., writing 1:1 for a clearly many-to-many case); confusing a relationship's descriptive attribute with an entity attribute.

    Chapter 3: Data and Process Modeling

    3.1 Introduction

    Data Modeling: Representing the data requirements of a system and the relationships among data items (e.g., via ERD).
    Process Modeling: Representing how data moves through and is transformed by the system's activities (e.g., via DFD).
    Data ModelingProcess Modeling
    Answers "what data exists and how is it related?"Answers "how does data flow and get transformed?"
    Tool: ERDTool: DFD
    Static viewDynamic view

    The two are complementary: DFD data stores correspond to ER entities; the data dictionary ties both together with consistent definitions.

    3.2 Overview of Data & Process Modeling Tools

    ToolPurposeMain ComponentsExample Use
    ERDModel data & relationshipsEntities, attributes, relationshipsDesigning a database schema
    DFDModel data flow/processesProcess, data flow, store, entityModeling an order-processing system
    Data DictionaryDocument every data element preciselyName, alias, description, structureDefining "Order ID" format
    Decision Table/TreeModel complex conditional logicConditions, actions, rulesLoan-approval logic

    3.3 Introduction to CASE Tools

    CASE (Computer-Aided Software Engineering): Software tools that automate/support activities of the systems development life cycle such as analysis, design, diagramming, and documentation.
    CategoryCoverage
    Upper CASESupports early phases — planning, analysis, design (diagramming)
    Lower CASESupports later phases — code generation, testing, maintenance
    Integrated/I-CASECovers the entire SDLC in one integrated toolset

    Features: diagramming (DFD/ERD/UML), central repository, code generation, documentation, consistency/error checking.

    Benefits: faster development, standardization, fewer errors, easier maintenance, better team communication.

    Limitations: high cost, training overhead, may not fit non-standard methodologies, tool lock-in.

    Examples: Visible Analyst, Rational Rose, StarUML, ERwin, Microsoft Visio (diagram-level).

    3.4 Role of CASE in Data Modeling

    • Diagram creation: Draws/edits ERD, DFD, UML with standard notation automatically.
    • Documentation: Auto-generates supporting documentation from diagrams.
    • Data-dictionary support: Maintains element definitions linked directly to diagram objects.
    • Consistency checking: Flags unbalanced DFDs, undefined data flows, orphan entities.
    • Repository: Central store of all project metadata reused across diagrams/phases.
    • Productivity & collaboration: Multiple analysts work on a shared model; changes propagate automatically; supports easier long-term maintenance.

    3.5 Data Dictionaries

    Data Dictionary: A centralized, structured repository that defines and describes every data element, data flow, and data store used in the system.

    Purpose/Importance: Removes ambiguity, ensures every analyst/developer uses the same definition, supports consistency-checking of DFDs and database design.

    Typical structure notation

    SymbolMeaning
    =is composed of
    +and
    [ | ]either/or
    { }iteration (repeats)
    ( )optional
    Worked example (based on the Library DFD in 2.4):
    Entry TypeNameDefinition
    Data FlowBook RequestBook Request = Member_ID + Book_ID
    Data StoreD1 Book FileBook File = {Book_ID + Title + Author + Status}
    Data ElementStatusStatus = [ "Available" | "Issued" ]

    Chapter 4: Logic Modeling

    4.1 Decision Table

    Decision Table: A tabular tool that lists all combinations of conditions and the corresponding actions to be taken — used to represent and verify complex conditional logic.

    Components: Condition stub (list of conditions), condition entries (Y/N per rule), action stub (list of possible actions), action entries (X = action taken), and rules (columns).

    Construction procedure

    1. List all conditions.
    2. List all possible actions.
    3. Compute number of rules = 2ⁿ (n = number of conditions).
    4. Fill in every Y/N combination.
    5. Mark the action(s) that apply to each rule.
    6. Simplify by merging rules with identical actions where a condition is irrelevant ("—").
    Problem: A shop gives a discount: if a customer is a member AND purchase ≥ Rs 5000 → 20% discount; if member only → 10%; if purchase ≥ Rs 5000 only → 5%; otherwise no discount.
    ConditionsR1R2R3R4
    Is Member?YYNN
    Purchase ≥ 5000?YNYN
    Actions
    20% discountX
    10% discountX
    5% discountX
    No discountX
    Interpretation: 2 conditions → 2²=4 rules, all covered, exactly one action per rule → table is complete (all combinations present) and consistent (no rule has conflicting/duplicate actions).

    Completeness/consistency check: Verify rule count = 2ⁿ, every rule has at least one action marked, and no two identical condition-columns lead to different actions.

    4.2 Decision Tree

    Decision Tree: A graphical tree representation of conditions and actions, where the root represents the starting decision point, branches represent condition outcomes, and leaves represent final actions.

    Components: Root (initial condition), Branches (paths for each condition outcome), Internal nodes (further conditions), Leaves (final actions/decisions).

    Decision TableDecision Tree
    Compact, good for many conditionsVisual, good for explaining sequence to non-technical users
    Easy to check completeness (2ⁿ rule count)Harder to verify completeness visually
    Harder to see sequential/priority logicNaturally shows order in which conditions are tested

    4.3 Structured English

    Structured English: A subset of English using a restricted set of keywords (IF/THEN/ELSE, DO, WHILE, CASE) and indentation, following a structured-programming style, to precisely describe a process's logic without full code syntax.

    Characteristics: Uses only sequence, selection, and iteration constructs; imperative verbs; no ambiguous adjectives/adverbs; indentation shows nesting.

    Converting the discount decision table to Structured English: 
    IF Customer IS Member THEN
    IF Purchase >= 5000 THEN
        Apply 20% Discount
    ELSE
        Apply 10% Discount
    ENDIF
ELSE
    IF Purchase >= 5000 THEN
        Apply 5% Discount
    ELSE
        Apply No Discount
    ENDIF
ENDIF

    When Structured English is preferable: When logic is largely sequential/nested (not purely combinatorial) and the audience needs something close to pseudocode/programmable logic; decision tables are preferable when there are many independent conditions needing a completeness check; decision trees are preferable for explaining sequential decision flow visually to non-technical users.

    Chapter 5: Object Modeling

    5.1 Overview of Object-Oriented Analysis (OOA)

    OOA: An analysis approach that models a system as a collection of interacting objects, each combining data and behavior, rather than as separate data and process models.
    TermMeaning
    ObjectAn instance of a class with its own state and behavior (e.g., a specific Student "Ram")
    ClassA blueprint/template defining common attributes & methods for a set of objects
    AttributeA data item describing an object's state
    Method/OperationA function/behavior an object can perform
    EncapsulationBundling data and methods together, hiding internal details
    AbstractionModeling only relevant features, hiding irrelevant complexity
    InheritanceA class acquiring attributes/methods of a parent (super)class
    PolymorphismSame operation behaving differently for different classes/objects

    These concepts let SAD move from separate data (ERD) and process (DFD) views into a single unified object model — the basis of UML.

    5.2 UML Class Diagram

    UML (Unified Modeling Language): A standardized graphical notation for visualizing, specifying, and documenting the artifacts of an object-oriented system.

    Class notation: a rectangle divided into 3 parts — Class Name / Attributes / Operations. Visibility: + public, − private, # protected.

    RelationshipMeaningNotation
    AssociationGeneral structural link between classesPlain line
    Aggregation"Has-a", whole-part but parts can exist independentlyLine with hollow diamond at whole end
    CompositionStrong "has-a"; part cannot exist without wholeLine with filled diamond at whole end
    Generalization/Inheritance"Is-a" relationshipLine with hollow triangle at parent end
    MultiplicityHow many instances relate (1, 0..1, 1..*, *, etc.)Numbers near line ends
    Worked example — Library System class diagram.
    1. Identify classes: Member, Book, Loan, Librarian
    2. Attributes: Member(memberID, name); Book(bookID, title, status); Loan(loanID, issueDate, dueDate)
    3. Methods: Member.borrowBook(); Book.checkAvailability(); Loan.calculateFine()
    4. Relationships: Member —(1..*)— Loan —(1)— Book (association); Librarian manages Book (association)
    5. Multiplicities: One Member can have many Loans (1 to 0..*); each Loan refers to exactly one Book

    5.3 State Diagram

    State Diagram: Shows the various states an object passes through during its lifetime and the events/transitions that cause it to move between states.

    Components: Initial state (●), State (rounded box), Transition (arrow labeled with event[guard]/action), Final state (◉).

    Example — Library Book object states: Available → (Issue event) → Issued → (Return event) → Available; Issued → (Overdue timer) → Overdue → (Return + Fine Paid) → Available; Book → (Damaged report) → Lost/Damaged (final).

    5.4 Sequence Diagram

    Sequence Diagram: Shows the time-ordered interaction between objects via messages, with each object's lifeline drawn vertically.

    Components: Objects/participants (top boxes), Lifelines (vertical dashed lines), Messages (horizontal arrows, time flows downward), Activation bars (rectangle on lifeline showing an object is executing), Return messages (dashed arrows).

    5.5 Use Case Diagram

    Use Case Diagram: Shows the functional requirements of a system as a set of use cases, the actors who interact with them, and the system boundary.
    ElementMeaning
    ActorA role (person/external system) that interacts with the system (stick figure)
    Use CaseA discrete unit of functionality the system provides (oval)
    System BoundaryRectangle marking what is inside vs outside the system
    AssociationLine connecting actor to use case
    «include»Base use case always incorporates the included use case (mandatory sub-behavior)
    «extend»An optional use case that may extend base behavior under a condition
    GeneralizationAn actor/use case that specializes another

    Identification steps: 1) Read requirements, find roles interacting with system → actors. 2) Find each distinct goal a user achieves → use cases. 3) Draw a boundary box separating system functions from external actors. 4) Connect each actor to the use case(s) it triggers. 5) Use «include» for mandatory shared steps (e.g., "Login" included in several use cases). 6) Use «extend» for optional/conditional behavior (e.g., "Pay Fine" only if overdue).

    Common UML mistakes: Confusing include (always happens, base depends on it) with extend (optional, base doesn't depend on it); drawing actors inside the system boundary; confusing state diagram (object lifecycle) with sequence diagram (interaction over time); missing multiplicities on class diagrams; using association where composition/aggregation is intended.

    Chapter 6: System Analysis

    6.1 System Planning and Initial Investigation

    System Planning: The activity of identifying, prioritizing, and scheduling candidate system projects aligned with organizational goals.
    Initial Investigation: A brief preliminary study conducted to understand the problem, define scope, and judge whether a full-scale analysis is worthwhile.

    Objectives: Clarify the request, identify the problem's nature, estimate scope/cost/benefit roughly, and recommend whether to proceed.

    Activities: Interview requester, review existing documents/reports, observe operation, define scope & constraints, identify stakeholders.

    Output: A short investigation report recommending: proceed to full feasibility study / modify request / reject.

    6.2 Project Scheduling

    Project Scheduling: Planning the timing, sequence, and resource allocation of project activities to complete the project within the estimated time.

    Importance: Controls delays, allocates resources efficiently, tracks progress against milestones.

    Key elements: Activities, Dependencies (which activity must finish before another starts), Milestones (checkpoints), Time estimates, Resources assigned.

    Gantt Chart: A horizontal-bar chart showing each activity's start/end dates and overlaps, used for tracking schedule progress.

    Worked example — simple schedule for a small module:
    ActivityDuration (days)Depends onStartEnd
    A: Requirement gathering5—Day 1Day 5
    B: Design4ADay 6Day 9
    C: Coding6BDay 10Day 15
    D: Testing3CDay 16Day 18
    Critical Path: The longest sequence of dependent project activities. It determines the minimum time required to complete the project. Any delay in a critical-path activity delays the project unless corrective action is taken.
    PERT (Program Evaluation and Review Technique): A network-diagram method for scheduling that shows tasks, dependencies, and estimated durations. It helps identify the critical path and is useful for complex projects with many dependencies.
    Critical Path worked example:
    Activities: A = 3 days (start), B = 4 days (after A), C = 2 days (after A), D = 3 days (after B and C).
    Paths: A→B→D = 3+4+3 = 10 days; A→C→D = 3+2+3 = 8 days.
    Critical Path = A→B→D; minimum project duration = 10 days.

    6.3 Requirement Analysis

    Requirement: A statement of what the system must do or a quality it must have. Requirement Analysis: The process of identifying, documenting, and validating user/business needs into precise specifications.

    Process: Requirement identification (elicit from stakeholders) → Documentation (write formal specification, e.g., SRS) → Validation (confirm with stakeholders/check for consistency & completeness).

    6.4 Types of Requirements

    TypeFocusStated ByExample
    Business RequirementsWHY — organizational goalsManagementIncrease revenue by 15%
    User RequirementsUser tasks/needsEnd usersSearch for a book by title
    Functional RequirementsWHAT — system functionsAnalystsSystem shall search by ISBN
    Non-Functional RequirementsHOW — qualityAnalysts/TechnicalSearch results in < 1 second
    User Requirements: Requirements from the end-user perspective describing the tasks users need to accomplish using the system. Example: “As a librarian, I need to search for a book by title or author.”
    Business Requirements: High-level statements of organizational goals and objectives — why the system is needed. Example: “Increase customer satisfaction by 20%.”
    TypeDefinitionExample
    Functional RequirementDescribes what the system must do — specific behaviors/functions"System shall allow a member to reserve a book"
    Non-Functional RequirementDescribes a quality/constraint on how the system performs its functions"System shall respond within 2 seconds", security, usability, reliability

    6.5 Requirement Gathering Methods

    MethodProcessAdvantagesDisadvantagesBest Suited When

    QuestionnaireWritten set of standard questions distributed widelyReaches many people cheaply, quick to analyzeNo follow-up/clarification, low response rateLarge, geographically spread user base

    6.6 Feasibility Study and Its Types

    Feasibility Study: An evaluation of whether a proposed system is practical and worthwhile, examined from multiple angles before committing full resources.
    TypeChecks
    Technical FeasibilityWhether required technology, hardware, software, and expertise are available/achievable
    Economic FeasibilityWhether benefits outweigh costs (see Cost-Benefit & Payback below)
    Operational FeasibilityWhether the system will be accepted and effectively used by the organization/staff
    Schedule/Time FeasibilityWhether the project can be completed within the required/available time frame
    Legal FeasibilityWhether the system complies with applicable laws, regulations, and standards, including data protection, copyright/licensing, and sector-specific requirements

    6.7 Steps of Feasibility Study

    1. Preliminary investigation of the problem/request
    2. Identify alternative solutions
    3. Analyze each alternative's feasibility (technical, economic, operational, schedule)
    4. Estimate costs and benefits of each alternative
    5. Evaluate and compare alternatives
    6. Prepare recommendation/feasibility report for management decision

    6.8 Cost/Benefit Analysis

    TermMeaningExample
    Direct CostCost clearly and directly attributable to the systemHardware purchase, software license, developer salary
    Indirect CostCost not directly tied to the system but incurred to support itElectricity, office space, general overhead
    Recurring CostOngoing operational costMonthly maintenance, annual license renewal, utilities
    One-Time CostCost incurred once during development or implementationHardware purchase, initial software license
    Tangible BenefitBenefit that can be measured in monetary termsReduced labor cost, faster processing saving Rs X/month
    Intangible BenefitBenefit that cannot be easily quantified in moneyImproved customer satisfaction, better decision quality
    Annual Net Benefit: Annual Benefits − Annual Costs
    Payback Period (uniform cash flow):
    Payback Period = Initial Investment ÷ Annual Net Benefit (net cash inflow)
    Applicable when the annual net cash inflow is the same every year.
    Easy worked problem: Initial investment = Rs 300,000. Annual net cash inflow = Rs 100,000 (uniform).
    Payback Period = 300,000 ÷ 100,000 = 3 years.
    Interpretation: The system recovers its investment cost in 3 years; management compares this against its acceptable payback threshold.
    Moderate worked problem (uneven cash flows — cumulative method): Initial investment = Rs 500,000.
    YearNet Cash Inflow (Rs)Cumulative Cash Flow (Rs)
    1100,000100,000
    2150,000250,000
    3200,000450,000
    4200,000650,000
    Step 1: Investment (500,000) is recovered between Year 3 (cum. 450,000) and Year 4 (cum. 650,000).
    Step 2: Remaining amount to recover at start of Year 4 = 500,000 − 450,000 = 50,000.
    Step 3: Fraction of Year 4 needed = 50,000 ÷ 200,000 = 0.25 year.
    Payback Period = 3 + 0.25 = 3.25 years.
    Interpretation: With uneven cash inflows, the simple division formula cannot be used directly — the cumulative method locates the year the cumulative inflow crosses the investment amount, then interpolates the fraction of the final year.

    Chapter 7: Systems Design

    7.1 Introduction to System Design

    System Design: The process of defining the architecture, modules, interfaces, and data for a system to satisfy specified requirements.

    Objectives: Translate logical requirements into a workable technical blueprint that is efficient, reliable, maintainable, and secure.

    Design activities: Architectural design, database design, interface/forms design, program/module design.

    Analysis defines what; design defines how — design activities directly build upon the requirement specification and models (DFD/ERD) produced during analysis.

    7.2 Process and Stages of System Design

    Requirements Specification → Architectural/High-level Design (subsystems, modules) → Detailed Design (module logic, data structures) → Database Design → Input/Output & Interface Design → Design Specification Document (handed to implementation team).

    7.3 Logical and Physical Design

    Logical DesignPhysical Design
    What the system must do, independent of technologyHow the system is technically implemented
    Focus: data & process requirementsFocus: hardware, DBMS, programming language, file structures
    Output: DFD, ERD, logical data modelOutput: DB schema, program specs, network layout
    Technology-independentTechnology-dependent

    Relationship: Logical design is refined into physical design once specific technology choices are made.

    7.4 Introduction to Structured Design

    Structured Design: A design approach that decomposes a system into hierarchically organized, independent modules connected via well-defined interfaces.

    Modular System Design

    Module: A self-contained unit of a program performing a specific task. Modularization: breaking a system into such modules.

    Benefits: easier to understand/develop/test/maintain; supports reuse; enables parallel team development.

    Principles: high cohesion within each module, low coupling between modules, single well-defined purpose per module.

    Functional Strength (Cohesion) — types, weakest to strongest

    TypeDescription
    Coincidental (weakest)Elements grouped with no meaningful relationship
    LogicalElements perform logically similar functions, selected by a flag/switch
    TemporalElements grouped because they execute at the same time (e.g., initialization)
    ProceduralElements grouped because they follow a certain sequence of steps
    CommunicationalElements operate on the same data/input
    SequentialOutput of one element is input to the next
    Functional (strongest)All elements contribute to a single well-defined task

    Structure Chart

    Structure Chart: A hierarchical diagram showing a system's modules, their call relationships (control flow), and the data/control passed between them.

    Components: Module (rectangle), Call (arrow top-down), Data couple (arrow with open circle = data passed), Control couple (arrow with filled circle = control flag passed).

    Worked example — Issue Book module decomposition:

    Cohesion vs Coupling

    Cohesion: The degree to which elements within a single module are functionally related — higher cohesion is better (see functional-strength table above).
    Coupling: The degree of interdependence between separate modules — lower coupling is better.
    Coupling TypeDescription (strongest/worst → weakest/best)
    Content coupling (worst)One module directly modifies/relies on another's internal data
    Common couplingModules share global data
    Control couplingOne module passes a control flag dictating another's logic
    Stamp couplingModules share a composite data structure, using only part of it
    Data coupling (best)Modules communicate only via simple parameter passing

    Why it matters: High cohesion + low coupling → modules are easy to understand, test, reuse, and modify independently, because a change inside one module rarely forces changes elsewhere. Low cohesion or high coupling increases the risk of ripple-effect errors during maintenance. It is not simply "high good / low bad" as an isolated slogan — cohesion should be high (functional strength), while coupling should be low (data coupling); each has multiple distinct sub-types with different implications, as tabulated above.

    7.5 Database Design and File Organization

    Database design translates the logical ER model into a physical schema — deciding tables, keys, indexes, storage. Major considerations: normalization, data integrity, storage efficiency, access speed, security.

    File OrganizationMeaningAdvantagesDisadvantagesSuitable Application
    SequentialRecords stored/accessed in a fixed physical order (e.g., by key)Simple, efficient for batch processing entire fileSlow for random access; must scan from startPayroll, batch billing
    Direct/RandomRecords accessed directly via a key mapped to an address (hashing)Very fast direct access to any recordWastes space; complex hashing; no natural orderReal-time lookup (e.g., seat reservation)
    Indexed-SequentialRecords stored sequentially plus an index for direct accessSupports both sequential and fast direct accessIndex maintenance overhead; more storageBanking/library systems needing both modes

    7.6 Input/Output and Forms Design

    Design AreaObjectives & Key Points
    Input DesignObjectives: accuracy, ease of entry, minimum keystrokes. Includes input validation (range, format, presence checks) and error prevention (default values, drop-downs, confirmation prompts).
    Output DesignObjectives: clarity, timeliness, right format for the audience (screen vs printed report), accuracy, only necessary detail.
    Forms DesignClear layout, grouped/labeled fields, logical tab order, inline validation messages, helpful guidance text, graceful error handling (specific messages, not generic "Error").

    Good practice example: A date field with a calendar picker and inline format hint (dd/mm/yyyy). Poor practice example: A free-text field with no format guidance that silently rejects invalid dates without explanation.

    Chapter 8: System Implementation

    8.1 Introduction to System Implementation

    System Implementation: The phase where the designed system is actually built/configured, tested, and put into operational use.

    Major activities: coding/configuration, testing, installation/conversion, training, documentation.

    8.2 System Installation and Its Types

    StrategyDefinitionAdvantagesDisadvantagesSuitable Situation
    Direct/ChangeoverOld system stopped, new system started immediatelyFast, low costHigh risk — no fallback if new system failsLow-risk system, small scale, or no old system exists
    ParallelOld and new systems run simultaneously for a periodSafe — can compare/fallback to old systemCostly, double effort/resourcesCritical systems where failure is unacceptable (e.g., banking)
    PilotNew system installed in one location/department firstLimits risk to a small area, real feedback before full rolloutSlower full deployment; pilot site may differ from othersMulti-branch organizations
    PhasedNew system introduced module-by-module or function-by-functionManageable risk, gradual user adaptationLonger overall implementation; interim interfacing needed between old/new partsLarge, complex systems built in modules

    8.3 System Quality and Software Quality Assurance

    Software Quality Assurance (SQA): Planned, systematic activities to ensure the software product meets defined quality standards.

    Quality Control vs Quality Assurance: QA is process-oriented (preventing defects through standards/procedures); QC is product-oriented (detecting defects in the actual product, e.g., via testing).

    TechniqueMeaning & ProcessParticipantsBenefits
    Formal Technical Review (FTR)A planned, structured meeting where technical staff evaluate a work product against specificationsProducer, reviewers, moderator, recorderEarly defect detection, technical accuracy check
    WalkthroughAuthor leads reviewers through the work product step by step, explaining logicAuthor, small group of peersInformal, quick feedback, knowledge sharing
    InspectionHighly formal, rule/checklist-based examination with defined roles and metrics collectionModerator, inspectors, reader, recorder (author often does not lead)Most rigorous — highest defect-detection rate

    Do not confuse: Walkthrough = author-led, informal; Inspection = checklist-driven, most formal, moderator-led; FTR = general term/structured review often used to describe either, but typically more formal than a walkthrough and often less rule-bound than a full inspection.

    8.4 & 8.5 System Maintenance and Its Process

    System Maintenance: Modifying a system after delivery to correct faults, adapt to new environments, improve performance, or prevent future problems.

    Need for maintenance: bugs discovered post-release, changing business/legal requirements, new hardware/OS environments, performance/security improvement needs.

    TypeDefinitionExample
    CorrectiveFixes actual defects/bugs found after releaseFixing a fine-calculation error
    AdaptiveModifies system to work in a new/changed environmentUpdating software for a new OS version
    PerfectiveImproves performance, usability, or adds enhancementsAdding a new report feature
    PreventiveMakes changes now to prevent future problemsRefactoring code to ease future updates

    Maintenance process (steps): 1) Identify/receive change request. 2) Analyze impact & feasibility. 3) Plan the modification. 4) Implement the change. 5) Test the modified system. 6) Update documentation. 7) Release/deploy the update. 8) Verify in production.

    8.6 Introduction to System Testing

    System Testing: The process of executing a system to find defects and verify it meets specified requirements before release.

    Purpose/Importance: Detect errors early, verify correctness, ensure reliability and user confidence before go-live.

    Testing objectives: Find as many defects as possible; verify functional and non-functional requirements are met; build confidence for deployment.

    Testing process: Test planning → Test-case design → Test execution → Defect logging → Retesting → Sign-off.

    Testing Level/TypeFocus
    Unit TestingIndividual module/function in isolation
    Integration TestingInteraction between combined modules
    System TestingComplete, integrated system against full requirements
    User Acceptance Testing (UAT)End users validate the system meets business needs before final sign-off

    3. Importance of Data & Data Management

    Definition

    Data is a collection of raw, unorganized facts (numbers, text, dates) that by itself carries no meaning until processed into information. Data management is the practice of collecting, storing, organizing, securing, and maintaining data so that it is accurate, available, and usable.

    Why data management matters:

    ReasonExplanation
    Decision makingAccurate, timely data lets organizations (banks, hospitals, colleges) make correct operational and strategic decisions.
    Avoiding redundancyProper management prevents the same data being duplicated inconsistently across files.
    Data integrityEnsures data remains accurate and consistent over its lifecycle (e.g., a student's CGPA is the same everywhere it appears).
    Security & privacyControlled access prevents unauthorized viewing/modification of sensitive data (e.g., patient records, bank balances).
    Sharing & concurrencyMultiple users/applications can access the same data simultaneously without conflict.
    RecoveryBackup/recovery mechanisms protect against data loss from crashes or disasters.

    Example: A university (Texas College of Management & IT type institution) manages student records, course enrollment, fee payment (e.g., via eSewa/Khalti-style digital payment integration), and grades. Poor data management would cause duplicate student IDs, lost marks, or incorrect fee balances — proper data management via a DBMS prevents this.

    4. How Data are Stored in a Database

    Data in a database is stored in a structured, organized form rather than as flat, disconnected files. The typical storage hierarchy is:

    LevelDescription
    BitSmallest unit — 0 or 1.
    Byte / CharacterGroup of bits representing a character.
    Field / Attribute / ColumnA single data item, e.g., StudentName.
    Record / Row / TupleA collection of related fields describing one entity instance, e.g., one student's full record.
    Table / File / RelationA collection of related records, e.g., the STUDENT table.
    DatabaseA collection of related tables, e.g., the whole college database (STUDENT, COURSE, DEPARTMENT...).

    Internally, the DBMS stores this data on secondary storage (disk) using data structures such as heap files, sorted files, hashed files, and indexes (B+ trees) to allow efficient retrieval — this is the physical storage layer, distinct from how the user logically views the data (see Section 5).

    5. Physical & Logical Structure of a Database

    Definition

    Physical structure refers to how data is actually stored on the storage device (disk blocks, file organization, indexing, access paths).
    Logical structure refers to how the data is organized and perceived by the user/application (tables, relationships, constraints) — independent of the physical storage details.

    This separation is called data independence:

    TypeMeaning
    Physical Data IndependenceAbility to change the physical storage/access method (e.g., adding an index) without changing the logical schema or applications.
    Logical Data IndependenceAbility to change the logical schema (e.g., adding a new table/column) without requiring changes to application programs that don't use that part of the schema.

    7. Database Management Systems (DBMS) vs Database Systems

    Definitions

    Database: An organized, persistent collection of related data.
    DBMS: Software that enables users to define, create, maintain, and control access to the database.
    Database System: The DBMS + the database itself + the application programs that use it — the complete environment.
    DatabaseDBMSDatabase System
    Just the stored data (e.g., student records file).The software (e.g., MySQL engine) that manages that data.Software + data + applications + users working together.

    Common Mistake

    Students often use "database" and "DBMS" interchangeably in exam answers — a database is data; a DBMS is the software that manages that data. Always distinguish them explicitly.

    9. Distributed Database vs Relational (Centralized) Database

    Classification Note (read before the table)

    "Relational" and "distributed" are answers to two different questions and are not opposite ends of the same scale:
    • Relational describes the data model — data organized into tables (relations) linked by keys, as opposed to hierarchical, network, or object models.
    • Distributed describes physical location — data spread across multiple sites, as opposed to centralized (single-site) storage.
    A database can therefore be: centralized + relational (e.g., a single-server MySQL college database), distributed + relational (e.g., a relational database replicated across multiple campus servers), or distributed + non-relational (e.g., a distributed NoSQL store). The table below specifically contrasts a centralized relational database with a distributed database to highlight the practical trade-offs of distribution — it is not claiming that "relational" and "distributed" are mutually exclusive categories.
    BasisRelational (Centralized) DatabaseDistributed Database
    LocationData resides at a single physical site.Data is stored across multiple, possibly geographically separated, sites.
    Data modelOrganized strictly into relations (tables) linked by keys.May be relational or otherwise; the defining trait is physical distribution, not the data model.
    Failure impactSingle point of failure — site failure makes the whole database unavailable.More fault tolerant — failure of one site need not bring down the whole system.
    ComplexitySimpler to design, manage, and query.More complex — needs distributed query processing, concurrency control, and replication.
    Performance for local usersUniform performance for all users regardless of location.Better performance for local queries (data closer to the user); slower for cross-site queries.
    CostLower infrastructure/network cost.Higher cost due to network and replication overhead.

    Common Mistake

    "Relational" describes the data model (tables/keys); "distributed" describes physical location. A database can be both relational and distributed at once — they are not mutually exclusive categories, so don't present them as if only one can be true.

    3. Entity, Relationship, and Object

    Definitions

    Entity: A real-world object or concept that can be distinctly identified and about which data is stored (e.g., STUDENT, COURSE).
    Entity Set: A collection of entities of the same type (e.g., all students).
    Attribute: A property that describes an entity (e.g., StudentName, RollNo).
    Relationship: An association between two or more entities (e.g., a STUDENT enrolls in a COURSE).
    Object: In object-oriented data modeling, an object is an identifiable instance that contains state (data/attributes) and may also contain behavior (methods). In basic ER modeling, the closer equivalent is an entity instance; ER itself models data structure rather than object behavior.

    Types of Attributes

    TypeDescriptionExample
    SimpleCannot be divided further.Age
    CompositeCan be broken into sub-parts.Name → FirstName + LastName
    Single-valuedHolds one value per entity.DateOfBirth
    Multi-valuedCan hold multiple values.PhoneNumbers
    DerivedComputed from another attribute.Age (derived from DOB)
    Key attributeUniquely identifies an entity.StudentID

    Cardinality and Participation

    ConceptMeaning
    CardinalityThe number of entity instances on each side of a relationship: One-to-One (1:1), One-to-Many (1:N), Many-to-Many (M:N).
    Participation — TotalEvery entity instance must participate in the relationship (double line in ER diagram).
    Participation — PartialEntity instances may or may not participate (single line).

    Example: A STUDENT enrolls in COURSE is Many-to-Many (a student takes many courses; a course has many students). A DEPARTMENT has HEAD-OF-DEPARTMENT is typically One-to-One.

    5. Importance of ER Diagram

    • Provides a clear visual blueprint of the database before implementation.
    • Helps identify entities, relationships, and constraints early, reducing costly design errors later.
    • Acts as a communication tool between database designers and non-technical stakeholders (e.g., college administration).
    • Forms the direct basis for deriving the logical (relational) schema — each entity typically becomes a table.
    • Helps enforce data integrity rules (cardinality, participation) at the design stage.

    6. Relational Model

    Definition

    The Relational Model, proposed by E. F. Codd (1970), represents data as a collection of two-dimensional tables called relations, where each row is a tuple and each column is an attribute. Relationships between data are represented by common values (keys) shared across tables, not by physical pointers.
    Relational TermInformal Equivalent
    RelationTable
    TupleRow / Record
    AttributeColumn / Field
    DegreeNumber of attributes (columns)
    CardinalityNumber of tuples (rows)
    DomainSet of allowable values for an attribute

    Keys in the Relational Model

    Key TypeDefinition
    Super KeyAny attribute/set of attributes that uniquely identifies a tuple.
    Candidate KeyA minimal super key (no redundant attribute).
    Primary KeyThe candidate key chosen to uniquely identify tuples in a relation; cannot be NULL.
    Alternate KeyCandidate key(s) not chosen as the primary key.
    Foreign KeyAn attribute in one relation that references the primary key of another relation, establishing a relationship.
    Composite KeyA primary key made of two or more attributes together.

    Example (ER → Relational mapping): The ER diagram above maps to relations:

    STUDENT(RollNo, Name, DOB)
COURSE(CourseCode, Title, Credit)
ENROLLS(RollNo, CourseCode, EnrollDate)   -- RollNo, CourseCode are foreign keys

    The Many-to-Many "Enrolls In" relationship becomes its own relation (ENROLLS) whose primary key is the combination of both foreign keys — this is the standard rule for converting M:N relationships to relational tables.

    Provides a clear conceptual overview before physical implementation.No standard notation — different tools/textbooks use slightly different symbols.

    8. Common Mistakes

    • Drawing a relationship diamond between two attributes instead of two entities.
    • Forgetting to resolve M:N relationships into a separate relation with a composite key.
    • Confusing "candidate key" with "primary key" — every primary key is a candidate key, but not vice versa.
    • Marking a foreign key as unique/primary in its own table when it need not be.

    4. Unary vs Binary Operators (Classification)

    CategoryOperatorsMeaning
    Unary OperatorsSelect (σ), Project (π), Rename (ρ)Operate on a single relation.
    Binary OperatorsUnion (∪), Intersection (∩), Set Difference (−), Cartesian Product (×), all Joins (⋈), Division (÷)Operate on two relations. Union, Intersection, and Set Difference additionally require the two relations to be union-compatible (same number of attributes, matching domains).

    5. SELECT (σ) — Selection

    Definition

    Selects rows (tuples) from a relation that satisfy a given condition. Symbol: σ condition(Relation). It is a horizontal operation — filters rows.
    σAge > 20(STUDENT)
    RollNoNameDeptIDAge
    S02BibekD221
    S04DiyaD322

    Exam note: Result relation has the same attributes as input, but only qualifying rows.

    Common Mistake

    Writing σ as if it removes columns — Select never removes columns, only rows. Column removal is Project's job.

    6. PROJECT (π) — Projection

    Definition

    Selects specified columns (attributes) from a relation, and removes duplicate rows from the result. Symbol: πattribute-list(Relation). It is a vertical operation.
    πName, DeptID(STUDENT)
    NameDeptID
    AayushD1
    BibekD2
    ChitraD1
    DiyaD3

    Common Mistake

    Forgetting that Project automatically eliminates duplicate rows in the result (since a relation is a set of tuples) — e.g. πDeptID(STUDENT) yields {D1, D2, D3}, not four rows with D1 repeated.

    7. RENAME (ρ)

    Definition

    Renames a relation and/or its attributes without changing its content. Symbol: ρNewName(Relation) or ρNewName(attr1,attr2,...)(Relation).
    ρPUPIL(ID, StudentName, DeptID, Age)(STUDENT)

    Produces a relation identical in content to STUDENT, but named PUPIL with RollNo renamed to ID and Name renamed to StudentName. Rename is essential before self-joins or Cartesian products between relations that share attribute names.

    8. UNION (∪)

    Definition

    Combines tuples from two union-compatible relations, producing a relation with all tuples from both, removing duplicates. Symbol: R ∪ S.

    Example: Let A = πRollNo(σDeptID='D1'(STUDENT)) = {S01, S03}, and B = πRollNo(σAge>20(STUDENT)) = {S02, S04}.

    A ∪ B = {S01, S02, S03, S04}

    9. INTERSECTION (∩)

    Definition

    Returns tuples that appear in both union-compatible relations. Symbol: R ∩ S.

    Using A and B above (both empty intersection here since D1 students {S01,S03} and Age>20 students {S02,S04} don't overlap): A ∩ B = {} (empty set). If instead C = πRollNo(σAge>19(STUDENT)) = {S01,S02,S04}, then A ∩ C = {S01}.

    10. MINUS / SET DIFFERENCE (−)

    Definition

    Returns tuples present in R but not in S. Symbol: R − S. Note R − S ≠ S − R (not commutative).
    A − B  where A={S01,S03}, B={S02,S04}  →  Result = {S01, S03}

    11. CARTESIAN PRODUCT (×)

    Definition

    Combines every tuple of relation R with every tuple of relation S, producing all possible pairings. Result has (rows of R × rows of S) tuples and (columns of R + columns of S) attributes.
    STUDENT × DEPARTMENT

    STUDENT has 4 rows, DEPARTMENT has 3 rows → result has 4×3 = 12 rows, each combining a student with every department (most combinations are meaningless until filtered by a matching condition — this is why Cartesian Product is almost always followed by a Select, forming a Theta Join).

    12. THETA JOIN (⋈θ)

    Definition

    Combines Cartesian Product and Selection: R ⋈θ S = σθ(R × S), where θ is any comparison condition (=, <, >, ≤, ≥, ≠), not necessarily equality.
    STUDENT ⋈STUDENT.DeptID = DEPARTMENT.DeptID AND STUDENT.Age > 20 DEPARTMENT

    This theta join first matches each student to the department with the same DeptID and also requires Age > 20. With the sample data, the matched students are S02 (Business, 22), S04 (Civil, 23), and S05 (Business, 21). The condition is meaningful because it relates attributes from both input relations.

    13. EQUIJOIN

    Definition

    A special case of Theta Join where the condition uses only the equality (=) operator.
    STUDENT ⋈STUDENT.DeptID = DEPARTMENT.DeptID DEPARTMENT

    14. NATURAL JOIN (⋈)

    Definition

    An Equijoin performed on all attributes common to both relations, with the duplicate join column automatically removed from the result. Symbol: R ⋈ S (no subscript).

    Common Mistake

    Saying Natural Join and Equijoin are identical — Natural Join is a specific type of Equijoin that (a) joins on all common attributes and (b) removes the duplicate column. A general Equijoin keeps both join columns and can join on any chosen equality condition, not necessarily all shared attributes.

    15. DIVISION (÷)

    Definition

    Given R(A,B) and S(B), R ÷ S returns all values of A in R that are associated with every value of B found in S. Used for "find X related to ALL Y" queries.

    Example: Find students enrolled in every course listed in a target set S = {C1, C2}.

    ENROLLS ÷ πCourseCode(σCourseCode IN ('C1','C2')(ENROLLS))

    From ENROLLS: S01→{C1,C2}, S02→{C1}, S03→{C1,C2}. Only S01 and S03 have both C1 and C2, so:

    Result = {S01, S03}

    16. Relational Calculus (Fundamentals)

    Note on Scope

    The syllabus title mentions "Relational Algebra & Calculus" but lists only algebra operators explicitly. The following covers the fundamental relational-calculus concepts as standard supplementary academic content (Silberschatz/Ramakrishnan) so the topic named in the chapter title is not left unaddressed — this is not an invented extended syllabus.

    Relational Calculus is a declarative query language — it describes what data to retrieve (using logical predicates), not how to retrieve it (unlike algebra's step-by-step procedure).

    TypeDescriptionNotation Style
    Tuple Relational Calculus (TRC)Variables range over tuples of a relation.{ t | P(t) } — "the set of tuples t such that predicate P(t) is true"
    Domain Relational Calculus (DRC)Variables range over individual domain values (attribute values) rather than whole tuples.{ <x1,x2,...> | P(x1,x2,...) }

    TRC Example: Find names of students in department D1:

    { t.Name | t ∈ STUDENT ∧ t.DeptID = 'D1' }

    DRC Example (same query): 

    { <n> | ∃ r, d, a ( <r,n,d,a> ∈ STUDENT ∧ d = 'D1' ) }

    Relational calculus is theoretically important because it is equivalent in expressive power to relational algebra (Codd's theorem) — every algebra expression has an equivalent calculus expression and vice versa. SQL itself is influenced by both: its procedural clause structure resembles algebra, while its declarative "describe the result" style resembles calculus.

    17. UNION ALL and INTERSECT (Set-Operator Distinctions)

    OperatorBehavior
    UNIONCombines two result sets and removes duplicates (matches pure relational-algebra Union, since a relation is a set).
    UNION ALLCombines two result sets and keeps duplicates — not a pure relational-algebra operator, but a practical SQL extension since SQL tables are technically multisets (bags), not strict sets.
    INTERSECTReturns rows common to both result sets — the SQL equivalent of relational-algebra Intersection.

    Common Mistake

    Assuming UNION ALL is "the same as UNION but faster" — they can return different row counts because UNION ALL retains duplicate rows while UNION eliminates them.

    18. Common Mistakes (Chapter-wide)

    • Using Select when a query actually needs Project (or vice versa) — Select filters rows, Project filters columns.
    • Forgetting union-compatibility requirement (same degree, matching domains) before applying ∪, ∩, or −.
    • Treating Equijoin and Natural Join as identical.
    • Confusing Division's purpose ("associated with ALL values") with a simple filter.

    5. SQL Execution Process

    StageWhat Happens
    1. ParsingSQL statement is checked for correct syntax and referenced objects (tables/columns) are validated.
    2. OptimizationThe query optimizer evaluates multiple possible execution plans (e.g., which index to use, join order) and picks the cheapest based on estimated cost.
    3. ExecutionThe chosen plan is executed by the database engine, accessing storage via the internal (physical) level.
    4. Result ReturnThe resulting rows are returned to the calling application/user.

    12. Developing Subqueries

    Definition

    A subquery (inner query/nested query) is a SELECT statement embedded inside another SQL statement's WHERE, FROM, or SELECT clause, used when a query's condition depends on the result of another query.

    Subquery with IN: Find names of students enrolled in course C1.

    SELECT Name FROM STUDENT
WHERE RollNo IN (SELECT RollNo FROM ENROLLMENT WHERE CourseCode = 'C1');
    Name
    Aayush Sharma
    Chitra Karki
    Aayush Sharma

    Subquery with comparison operator: Find students older than the average student age.

    SELECT Name, Age FROM STUDENT
WHERE Age > (SELECT AVG(Age) FROM STUDENT);

    Average age = (20+22+19+23+21)/5 = 21. So result: Bibek Thapa (22), Diya Gurung (23).

    Correlated subquery: Find courses whose credit is the maximum within courses taught by the same instructor.

    SELECT Title FROM COURSE C1
WHERE Credit = (SELECT MAX(Credit) FROM COURSE C2 WHERE C2.InstructorID = C1.InstructorID);

    Unlike a simple subquery (executed once), a correlated subquery re-executes for each row of the outer query because it references the outer query's table (C1) inside the inner query.

    Common Mistake

    Using = instead of IN when a subquery can return multiple rows — WHERE RollNo = (SELECT RollNo FROM ENROLLMENT WHERE CourseCode='C1') would error out or behave unpredictably since the subquery returns three rows, not one.

    Chapter 5 — Conceptual Design

    1. Chapter Overview

    Conceptual design is the first phase of database design: understanding what the organization needs from the database, before any table structures or physical storage decisions are made. Output of this phase is typically an ER diagram representing entities and relationships in business terms.

    2. Syllabus Coverage Checklist

    • Conceptual Design Process

    3. Conceptual Design Process

    Definition

    Conceptual design is the process of building a high-level, implementation-independent model of the data requirements of an organization, describing what data must be stored and how it relates, without deciding how it will be physically implemented in a specific DBMS.
    StepActivity
    1. Requirement gatheringInterview stakeholders, review existing forms/reports/documents to understand what data the organization needs.
    2. Requirement analysisOrganize gathered requirements into a clear list of data objects, their properties, and business rules.
    3. Identify entities and relationshipsFrom the analyzed requirements, identify candidate entities, their attributes, and how entities relate.
    4. Build the ER modelDraw the ER diagram capturing entities, attributes, relationships, cardinality, and participation constraints.
    5. Review with stakeholdersValidate the conceptual model against real business requirements before proceeding to logical design.

    4. Requirement Analysis

    Definition

    Requirement analysis is the systematic study of what data an organization needs to store, how that data will be used, and what business rules/constraints govern it.

    Techniques used: interviews with users, questionnaires, studying existing documents/forms (e.g., a college's existing paper admission form, fee receipt), observing current workflows.

    Example (college admission system): Requirement analysis for a college might reveal: "Each student belongs to exactly one department," "A student can enroll in many courses," "Each course is taught by exactly one instructor at a time," and "Fee payments must be tracked per student per semester." These become the raw material for identifying entities and relationships.

    5. Identify the Relation (Identifying Entities and Relationships)

    Terminology note

    The syllabus phrase Identify the Relation is treated here as the design step of identifying the relevant data objects/entities and their relationships from requirements. At this stage, the designer is not yet finalizing physical tables; the relational schema is developed during logical design.

    From the analyzed requirements, the designer identifies:

    From Requirement StatementIdentified As
    Nouns describing a real-world object with independent existence ("student," "course," "department")Entities
    Properties describing an entity ("name," "age," "credit hours")Attributes
    Verbs/phrases linking two entities ("enrolls in," "teaches," "belongs to")Relationships
    Statements about how many of one entity relate to another ("a student can enroll in many courses")Cardinality

    Worked example: Requirement: "The college has students who enroll in courses. Each course is taught by one instructor. Each student belongs to exactly one department." This yields:

    • Entities: STUDENT, COURSE, INSTRUCTOR, DEPARTMENT
    • Relationships: STUDENT–enrolls in–COURSE (M:N), INSTRUCTOR–teaches–COURSE (1:N), STUDENT–belongs to–DEPARTMENT (N:1)

    This directly matches the ER diagram and relational schema developed in Chapter 2, confirming the pipeline: requirements → entities/relationships → ER diagram → relational schema (Chapter 6).

    6. Common Mistakes

    • Jumping straight to table design without first analyzing requirements — leads to missing entities/attributes discovered too late.
    • Confusing an attribute for an entity (e.g., treating "Department" as just a text attribute of Student when it actually needs its own entity with its own attributes like DeptName, Head).
    • Skipping stakeholder validation of the conceptual model.

    3. Logical Design Process

    Definition

    Logical design is the process of converting the conceptual ER model into a logical schema composed of relations (tables), expressed independent of any particular DBMS product, but fully specifying tables, attributes, keys, and constraints.
    StepActivity
    1. Review/refine ER diagramConfirm entities, attributes, relationships, and cardinalities are finalized from conceptual design.
    2. Map entities to tablesEach strong entity becomes a table; its attributes become columns.
    3. Map relationships1:N relationships → foreign key placed on the "many" side; M:N relationships → a new bridge/junction table.
    4. Define primary keysChoose the primary key for each table from its candidate keys.
    5. Define foreign keys/constraintsAdd referential integrity constraints, NOT NULL, UNIQUE, CHECK as needed.
    6. Validate against requirementsEnsure the logical schema fully supports the queries/business rules identified during conceptual design.

    5. Create Tables and Constraints

    CREATE TABLE DEPARTMENT (
  DeptID    CHAR(3) PRIMARY KEY,
  DeptName  VARCHAR(50) NOT NULL UNIQUE

CREATE TABLE STUDENT (
  RollNo   CHAR(3) PRIMARY KEY,

  CONSTRAINT fk_student_dept FOREIGN KEY (DeptID) REFERENCES DEPARTMENT(DeptID)
);

  CourseCode  CHAR(3) PRIMARY KEY,

  Credit      INT
);

  RollNo      CHAR(3),
  CourseCode  CHAR(3),

  FOREIGN KEY (RollNo) REFERENCES STUDENT(RollNo),
  FOREIGN KEY (CourseCode) REFERENCES COURSE(CourseCode)
);
    ConstraintPurpose
    PRIMARY KEYUniquely identifies each row; implicitly NOT NULL + UNIQUE.
    FOREIGN KEYEnforces that a value must exist in the referenced table's primary key (referential integrity).
    NOT NULLDisallows missing values for that column.
    UNIQUEPrevents duplicate non-NULL values; NULL handling is DBMS-dependent. Unlike PRIMARY KEY, UNIQUE does not generally imply NOT NULL.
    CHECKEnforces a custom condition on column values (e.g., Age > 0).

    6. Create Referential Keys (Referential Integrity)

    Definition

    Referential integrity is the rule that a foreign key value in a child table must either match an existing primary key value in the parent table, or be NULL. This prevents "orphan" records that reference nonexistent parent rows.
    -- This INSERT fails referential integrity because 'D9' does not exist in DEPARTMENT:
INSERT INTO STUDENT VALUES ('S06','Rita Basnet','D9',20);
-- ERROR: foreign key constraint fails

-- Referential actions can be specified for updates/deletes:
FOREIGN KEY (DeptID) REFERENCES DEPARTMENT(DeptID)
  ON DELETE CASCADE
  ON UPDATE CASCADE;
    Referential ActionEffect on Child Rows When Parent Row Is Deleted/Updated
    CASCADEAutomatically delete/update matching child rows.
    SET NULLSet the foreign key in child rows to NULL.
    RESTRICT / NO ACTIONPrevent the delete/update if matching child rows exist.

    7. Common Mistakes

    • Forgetting to declare foreign keys — this loses referential integrity enforcement even if data happens to be consistent initially.
    • Placing the foreign key on the wrong side of a 1:N relationship (it always goes on the "many" side).
    • Not defining a composite primary key for a resolved M:N junction table (e.g., ENROLLMENT), which then allows duplicate enrollment rows.

    1. Chapter Overview

    3. Use of Normalization (Why We Normalize)

    Definition

    Normalization is the systematic process of decomposing relations to eliminate redundancy and the anomalies that redundancy causes, guided by functional dependencies among attributes.

    Problems solved by normalization (anomalies in an unnormalized relation):

    AnomalyDescriptionExample
    Update AnomalyThe same fact is stored in multiple rows; updating it in only one place leaves the data inconsistent.If a course's title is repeated in every enrollment row and you fix a typo in one row but not others, the title becomes inconsistent.
    Insertion AnomalyCannot insert a fact about one entity without also having data about another, unrelated entity.Cannot add a new course unless at least one student has already enrolled in it, if course details are only stored inside the enrollment table.
    Deletion AnomalyDeleting a row unintentionally removes other, still-needed information.If the only student enrolled in a course is deleted, the course's details are lost too.

    Functional Dependency (FD): An attribute B is functionally dependent on attribute A (written A → B) if each value of A is associated with exactly one value of B. FDs are the formal basis for identifying normalization violations.

    4. Different Forms of Normalization — Worked Example

    Unnormalized Relation (UNF) — a college enrollment report, one row per student holding multiple courses in a single cell:

    RollNoStudentNameDeptIDDeptNameCourses (CourseCode, Title, Credit)
    S01Aayush SharmaD1Computer Science(C1, DB Mgmt, 3), (C2, Prog. Fund., 4)
    S02Bibek ThapaD2Business(C3, Marketing, 3)

    This is unnormalized because the "Courses" column holds a repeating group (multiple values per cell) — it violates the very definition of a relation, where each cell must hold a single atomic value.

    Step 1 — First Normal Form (1NF)

    Rule

    A relation is in 1NF if every attribute contains only atomic (indivisible) values, and there are no repeating groups.

    Transformation: flatten the repeating "Courses" group into separate rows.

    RollNoStudentNameDeptIDDeptNameCourseCodeTitleCredit
    S01Aayush SharmaD1Computer ScienceC1DB Mgmt3
    S01Aayush SharmaD1Computer ScienceC2Prog. Fund.4
    S02Bibek ThapaD2BusinessC3Marketing3

    Call this relation ENROLL_REPORT(RollNo, StudentName, DeptID, DeptName, CourseCode, Title, Credit). Primary key: (RollNo, CourseCode) — composite, since neither alone is unique.

    Functional dependencies present:

    RollNo → StudentName, DeptID, DeptName      (partial — depends only on RollNo, part of the key)
DeptID → DeptName                            (transitive — DeptName depends on DeptID, not directly on the key)
CourseCode → Title, Credit                   (partial — depends only on CourseCode, part of the key)
(RollNo, CourseCode) → (all attributes)      (full functional dependency on the whole key)

    Step 2 — Second Normal Form (2NF)

    Rule

    A relation is in 2NF if it is in 1NF and has no partial dependency — i.e., no non-key attribute depends on only part of a composite primary key. (2NF is only a concern when the primary key is composite.)

    Problem in ENROLL_REPORT: StudentName, DeptID, DeptName depend only on RollNo (part of the key); Title, Credit depend only on CourseCode (the other part) — both are partial dependencies.

    Decomposition to remove partial dependencies:

    STUDENT_2NF(RollNo, StudentName, DeptID, DeptName)
COURSE_2NF(CourseCode, Title, Credit)
ENROLLS_2NF(RollNo, CourseCode)

    Now every non-key attribute in STUDENT_2NF and COURSE_2NF depends on the whole (single-attribute) key of its own table, and ENROLLS_2NF holds only the composite key linking them. 2NF is satisfied.

    Step 3 — Third Normal Form (3NF)

    Rule

    A relation is in 3NF if it is in 2NF and has no transitive dependency — i.e., no non-key attribute depends on another non-key attribute (rather than depending directly on the primary key).

    Problem in STUDENT_2NF(RollNo, StudentName, DeptID, DeptName): DeptName depends on DeptID, and DeptID depends on RollNo — so DeptName depends on RollNo only transitively, through DeptID. This still causes an update anomaly (fixing a department's name requires updating it in every student row belonging to that department).

    Decomposition to remove the transitive dependency:

    STUDENT_3NF(RollNo, StudentName, DeptID)
DEPARTMENT_3NF(DeptID, DeptName)
COURSE_3NF(CourseCode, Title, Credit)
ENROLLS_3NF(RollNo, CourseCode)

    Now every non-key attribute in every relation depends directly and only on its own table's primary key. All four relations are in 3NF.

    5. Summary Table of Normal Forms

    Normal FormConditionRemoves
    1NFAll attributes atomic; no repeating groups.Multi-valued/composite cells.
    2NF1NF + no partial dependency on a composite key.Non-key attributes depending on only part of the key.
    3NF2NF + no transitive dependency.Non-key attributes depending on other non-key attributes.

    Note on Scope

    The syllabus lists "different forms of normalization" without naming BCNF/4NF/5NF explicitly. 1NF, 2NF, and 3NF are covered in full worked detail above as the syllabus-required forms. If your instructor's slides also require Boyce-Codd Normal Form (BCNF), note it briefly as supplementary: BCNF strengthens 3NF by requiring that for every non-trivial FD X→Y, X must be a superkey (this matters mainly when a relation has multiple overlapping candidate keys — a case not present in the example above).

    6. Common Mistakes

    • Trying to check for 2NF violations when the primary key is a single attribute (partial dependency is only possible with a composite key).
    • Confusing partial dependency (depends on part of the key) with transitive dependency (depends on a non-key attribute).
    • Decomposing a relation without checking that the decomposition is lossless (i.e., joining the decomposed relations back together via natural join must reproduce the original data exactly).
    • Stopping at 1NF and assuming redundancy is gone — 1NF alone does not remove partial or transitive dependencies.

    AdvantageExplanation
    Improved reliability/availabilityFailure of one site does not necessarily bring down the entire system — other sites continue operating.

    Higher costAdditional cost for network infrastructure, replication storage, and more complex software.
    Security challengesData traveling across networks between sites is more exposed to interception than data confined to one machine.
    Data consistency difficultyKeeping replicated copies synchronized across sites (especially during concurrent updates) is technically challenging.
    Dependency on networkNetwork failure can isolate sites or prevent cross-site transactions from completing.

    • Confusing "distributed database" with "distributed computing" in general — the former specifically concerns data storage/management across sites.

    Chapter 10 — Database Evaluation and Transaction

    1. Chapter Overview

    A transaction is the fundamental unit of work in a DBMS. This chapter explains transaction management, the ACID properties that guarantee transaction correctness, and the process of database evaluation.

    2. Syllabus Coverage Checklist

    • Transaction Management
    • ACID Properties
    • Database Evaluation Process

    3. Transaction and Transaction Management

    Definition

    A transaction is a logical unit of work comprising one or more database operations (reads/writes) that must be executed as an indivisible whole — either all operations succeed and are permanently saved, or none of them take effect.

    Example transaction — bank transfer of NPR 5000 from Account A to Account B:

    BEGIN TRANSACTION;
  UPDATE ACCOUNT SET Balance = Balance - 5000 WHERE AccNo = 'A';
  UPDATE ACCOUNT SET Balance = Balance + 5000 WHERE AccNo = 'B';
COMMIT;

    If the system crashes after the first UPDATE but before the second, transaction management ensures the entire transaction is rolled back — Account A's balance is restored — rather than leaving money "lost" between the two updates.

    Transaction States

    StateMeaning
    ActiveTransaction is currently executing its operations.
    Partially CommittedAll operations executed; changes not yet made permanent.
    CommittedTransaction completed successfully; changes permanently saved.
    FailedAn error occurred and normal execution cannot continue.
    AbortedTransaction rolled back; database restored to its state before the transaction began.

    Transaction management is the DBMS's responsibility to coordinate concurrent transactions (via concurrency control, e.g., locking) and ensure crash recovery (via logging), so that the ACID properties below always hold.

    4. ACID Properties

    Definition

    ACID is the set of four properties that guarantee reliable processing of database transactions: Atomicity, Consistency, Isolation, Durability.
    PropertyMeaningPractical ExampleWhy It Matters
    AtomicityA transaction executes completely or not at all — "all or nothing."In the bank transfer, either both the debit and credit happen, or neither does.Prevents partial updates that would leave data inconsistent (e.g., money deducted but never credited).
    ConsistencyA transaction takes the database from one valid state to another, preserving all defined rules/constraints.Total money in the bank (sum of all balances) is the same before and after the transfer.Guarantees business rules and constraints (e.g., CHECK, referential integrity) are never violated by a transaction.
    IsolationConcurrent transactions execute as if they ran one at a time (serially), even though they may actually interleave.Two customers withdrawing from the same account simultaneously don't see each other's uncommitted changes and don't cause an incorrect final balance.Prevents concurrency anomalies like dirty reads, lost updates.
    DurabilityOnce a transaction commits, its changes survive permanently, even in the event of a system crash.After the transfer is committed, a power failure the next second does not undo the transfer.Guarantees committed work is never lost.

    Common Mistake

    Confusing Consistency (a database-rule-preservation property) with Isolation (a concurrency-control property) — Consistency is about constraints being respected; Isolation is about concurrent transactions not interfering with each other.

    5. Database Evaluation Process

    Definition

    Database evaluation is the process of assessing an implemented database system against defined criteria — performance, correctness, security, usability — to verify it meets the organization's requirements before/after deployment.
    StepActivity
    1. Define evaluation criteriaEstablish what "success" means: query response time, data accuracy, security compliance, ease of use.
    2. Functional testingVerify that the database correctly supports all required operations (CRUD, reports, constraints).
    3. Performance testingMeasure query response times, throughput under expected load, and indexing effectiveness.
    4. Data integrity/security reviewConfirm constraints, referential integrity, and access-control rules work as intended.
    5. User acceptanceConfirm real users can complete required tasks correctly and efficiently.
    6. Report and refineDocument findings and refine schema, indexing, or queries as needed.

    Example: Before going live, a college database is evaluated by checking whether enrollment queries return correct results, whether fee-payment transactions are processed within an acceptable time, and whether unauthorized users are correctly denied access to student grade records.

    6. Common Mistakes

    • Treating "Consistency" in ACID as the same as "consistency" in the CAP theorem (a different, distributed-systems concept) — in ACID it specifically means preserving declared database constraints.
    • Believing atomicity guarantees correctness of business logic — atomicity only guarantees all-or-nothing execution, not that the logic itself is correct.
    • Skipping database evaluation after deployment, assuming a working demo means the system is production-ready under real load.

    A web crawler (spider/bot) is a program that systematically browses the web, downloading pages and following hyperlinks to discover new pages, in order to build/update a search engine's index.
    StepDescription
    1. Start with seed URLsBegin from a known set of starting web addresses.
    2. Fetch the pageDownload the page's HTML content via HTTP request.
    3. Extract linksParse the HTML to find all hyperlinks (<a href>) on the page.
    4. Store/index the pageSave the page content for indexing by the search engine.
    5. Queue new linksAdd newly discovered, not-yet-visited URLs to a queue (respecting rules like robots.txt, avoiding duplicate visits).
    6. RepeatContinue fetching from the queue until it is empty or a crawl budget/depth limit is reached.

    Applications: search engines (Google, Bing), price-comparison sites, and academic citation databases all rely on crawling to keep their underlying data current.

    6. Common Mistakes

    • Confusing "web search" (the end-user retrieval process backed by a pre-built index) with "web crawling" (the background process of discovering/downloading pages to build that index) — crawling happens before search, not during it.
    • Assuming a crawler visits the entire web in one pass — in practice, crawling is continuous and prioritized/rate-limited.

    7. Exam Focus

    Normalization Practice Section

    Q1. The following unnormalized relation records hospital patient visits. Normalize it to 3NF.

    PATIENT_VISIT_UNF(PatientID, PatientName, DoctorID, DoctorName, DoctorSpecialty, VisitDate, Diagnosis) — Primary key attempt: (PatientID, VisitDate). Assume: PatientID → PatientName; DoctorID → DoctorName, DoctorSpecialty; (PatientID, VisitDate) → DoctorID, Diagnosis.

    Step 1 (1NF): All attributes are already atomic (no repeating groups) — relation is in 1NF as given.

    Step 2 (2NF): Primary key is composite: (PatientID, VisitDate). Check partial dependencies: PatientName depends only on PatientID (part of key) → partial dependency. DoctorID, DoctorName, DoctorSpecialty are functionally determined via DoctorID which itself is determined by the full key (PatientID,VisitDate) → DoctorID is fully dependent, but DoctorName/DoctorSpecialty depend on DoctorID (non-key), which is actually a transitive issue we'll resolve in 3NF. First remove the direct partial dependency:

    PATIENT(PatientID, PatientName)
VISIT_2NF(PatientID, VisitDate, DoctorID, DoctorName, DoctorSpecialty, Diagnosis)

    Step 3 (3NF): In VISIT_2NF, DoctorName and DoctorSpecialty depend on DoctorID, not directly on (PatientID, VisitDate) — a transitive dependency. Remove it:

    PATIENT(PatientID, PatientName)
DOCTOR(DoctorID, DoctorName, DoctorSpecialty)
VISIT(PatientID, VisitDate, DoctorID, Diagnosis)

    Result: Three relations, each in 3NF — PATIENT and DOCTOR hold entity data; VISIT holds the fact/event data linking them.

    Q2. Given LIBRARY_UNF(BookID, BookTitle, MemberID, MemberName, MemberAddress, IssueDate), with BookID → BookTitle; MemberID → MemberName, MemberAddress; (BookID, MemberID) → IssueDate — identify the normal form violated and normalize to 3NF.

    Analysis: Primary key = (BookID, MemberID) (composite, assuming a book can be issued to different members over time and this table tracks current issues). BookTitle depends only on BookID (partial); MemberName, MemberAddress depend only on MemberID (partial). This violates 2NF.

    Decomposition:

    BOOK(BookID, BookTitle)
MEMBER(MemberID, MemberName, MemberAddress)
ISSUE(BookID, MemberID, IssueDate)

    All three relations are now in 3NF — no partial or transitive dependencies remain.

    Normalization Quick Reference

    1NF: atomic values, no repeating groups → 2NF: 1NF + no partial dependency → 3NF: 2NF + no transitive dependency. Always verify decomposition is lossless (natural join of decomposed relations reproduces the original).

    ACID Properties — Quick Revision

    Atomicity (all-or-nothing) · Consistency (constraints preserved) · Isolation (concurrent transactions don't interfere) · Durability (committed changes survive crashes).

    Distributed Database Quick Reference

    Advantages: reliability, local autonomy, local performance, scalability, matches org structure. Disadvantages: complexity, cost, security exposure, consistency difficulty, network dependency.

    Web/Database Quick Reference

    Three-tier: Client → App/Web Server → Database Server. Web search = Crawler → Indexer → Query Processor → Ranking Engine (inverted index). Web crawling = seed URLs → fetch → extract links → store/index → queue → repeat.

    VSQA — 2 Marks

    2MCh1: What is the internal (physical) level of the three-schema architecture?
    The level describing how data is actually stored on disk (files, blocks, indexes).
    2MCh2: What is a weak entity?
    An entity that cannot be uniquely identified by its own attributes alone and depends on a related "owner" entity for identification.
    2MCh3: What is union-compatibility?
    Two relations have the same number of attributes with matching domains, allowing ∪, ∩, and − to be applied.
    2MCh4: What is the purpose of the ORDER BY clause?
    To sort the result set of a query by one or more columns, ascending or descending.
    2MCh5: What is requirement analysis?
    The systematic study of what data an organization needs and the business rules governing it, done before designing the database.
    2MCh6: What does "create referential keys" mean in logical design?
    Defining foreign keys that enforce referential integrity between related tables.
    2MCh7: Why is 2NF only relevant when the primary key is composite?
    Partial dependency (the violation 2NF removes) can only exist when a non-key attribute depends on part of the key — impossible with a single-attribute key.
    2MCh8: What is a cloud database?
    A database hosted and managed on cloud infrastructure offering elastic scaling (e.g., Amazon RDS).
    2MCh9: What is replication in a distributed database?
    Storing copies of the same data at multiple sites to improve availability and local read performance.
    2MCh10: What is the "partially committed" transaction state?
    The state where all transaction operations have executed, but changes are not yet made permanent.
    2MCh11: What question does predictive data analysis answer?
    "What is likely to happen?" — based on historical patterns.
    2MCh12: What is the role of an indexer in web search?
    It processes crawled pages and builds an inverted index mapping keywords to the pages containing them.
